## Engine source, verified (primary — read from `sgl-project/sglang` main, `kvcache-ai/sglang` main, `kvcache-ai/ktransformers` main via Librarian, and from the two pulled images, 2026-09-21)

Feeds `plan/E6-DESIGN.md` §3/§4/§8 and T3.5b.

- **Upstream SGLang already carries the KT hybrid glue.** `python/sglang/srt/layers/moe/kt_ep_wrapper.py::KTEPWrapperMethod(FusedMoEMethodBase)` wraps any GPU MoE method; `FusedMoE` (`fused_moe_triton/layer.py`) installs it when `--kt-weight-path` is set; `deepseek_v4.py` imports it by side effect; `decode_cuda_graph_runner.py` calls `KTMoEWrapper.set_capture_batch_sizes(...)` before capture. Server args `--kt-weight-path --kt-method --kt-cpuinfer --kt-threadpool-count --kt-num-gpu-experts --kt-max-deferred-experts-per-token` exist (`server_args.py` ≈ L3160–3180 in the image). **In the `dev-dsv41` image (`da64c5cb`) this wrapper is the minimal 393-line version**: contiguous split (`topk_ids[topk_ids >= num_gpu_experts] = -1`), `assert activation == "silu"`, rank-0-only CPU, and `set_capture_batch_sizes(self.capture_bs)` — *not* `bs × num_tokens_per_bs` as on current main (matters for DSpark verify shapes). No placement strategies, no dynamic update, no layerwise prefill.
- **The KT fork's wrapper is the full one**: 6,212 lines in `approachingai/ktransformers:DSV4-specific` with `_Mxfp4LayerwisePrefillManager` (double-buffered pinned MXFP4 slots + Marlin-prepared slots; each TP rank DMA-copies its own slice; gated to CC (8,9) and (12,0)), `SharedStagingBuffer`, placement strategies (`uniform`, `front-loading`, `random`, `frequency`), dynamic expert update (**skipped for MXFP4**). `--kt-num-gpu-experts` is **per MoE layer** (multiplied by the MoE layer count into a `[layers, experts]` mask). Fork models: `deepseek_v4` only (`model_type = "deepseek_v4"`, `SGLANG_DSV4_MODE=2604`); no V4.1.
- **CPU call is CUDA-graph capturable.** `kt-kernel/cpu_backend/cpuinfer.h` uses `cudaLaunchHostFunc` for `submit_with_cuda_stream` / `sync_with_cuda_stream`; no `cudaStreamAddCallback`. KT allocates pinned input/id/weight/output buffers once per registered capture size (`experts_base.py`).
- **TP2 does not duplicate CPU work**: only rank 0 constructs `KTMoEWrapper`; other ranks return zeros and the model's TP all-reduce sums.
- **MXFP4 CPU path reads the checkpoint directly.** `kt-kernel/python/utils/loader.py::MXFP4SafeTensorLoader` expects `layers.N.ffn.experts.E.w{1,2,3}.{weight,scale}` (probes `model.layers.N` and `layers.N`); weights kept as packed `uint8`, UE8M0 scales losslessly shifted to BF16 (`(s << 7)` reinterpret). Kernel `operators/amx/fp4-moe.hpp` needs AVX-512F/BW/BF16 (Zen 5 has all three; AMX not required), fallback `operators/avx2/mxfp4-moe.hpp`. Resolves open question 7 for the KT side: no repack, bit-identical weights. (kt-kernel 0.7.0.post4 also lists `NVFP4` and an `NVFP4SafeTensorLoader`, so an NVFP4 conversion *could* run on the CPU tier; we still choose MXFP4 because it is the trained format and the smaller checkpoint — see PROVENANCE.md.)
- **kt-kernel wheel works in `dev-dsv41`.** `kt-kernel==0.7.0.post4` (`cp312-manylinux_2_35`) metadata pins `torch==2.9.1`, but the extension `.so` links only gomp/hwloc/mvec/numa/udev — `pip install --no-deps` into the torch 2.13.0+cu130 image imports and selects `_kt_kernel_ext_avx512_bf16`. No source build needed.
- **V4.1 routed experts upstream** are `Fp8Config`/`Fp8MoEMethod` with `is_fp4_expert=True` (from `routed_experts_quant_method == "mxfp4"` in `model_config.py`), weights `int8 [E, 2I, H/2]`. Auto backend for DeepSeek-V4 on SM90/100/120 is `flashinfer_mxfp4`; on SM120 that is **FlashInfer CUTLASS `cutlass_fused_moe` MXFP8 × MXFP4 (`_fi_kernel = "cutlass_sm120"`)** — TRT-LLM FP4 MoE is SM100-only. `marlin` and `triton_kernels` remain selectable. Resolves open question 3 for the SGLang engine: native block-scaled, W4A8 (MXFP8 activations). V4/V4.1 MoE activation is `silu` (KT's assertion holds).
- **CSA2 on SM120 at TP2 is dispatchable.** FlashInfer 0.6.18 `flashinfer/mla/_sparse_mla_sm120.py`: `_DECODE_MAX_TOKENS = 64`, `_DECODE_DSV4_DISPATCH` includes `(32, {128,192,256,512,1024})` — 32 local heads (64 / TP2) are covered; SGLang's `flash_mla_sm120.py` reads that table and splits 256-token pages into 64-token pages for the FlashInfer fast path.

## SM120 kernel status (secondary, read 2026-09-21)

- **Hardware/CUTLASS.** SM120 has hardware block-scaled `mma.sync` (Colfax, "NVFP4 blockscaled GEMM on SM12x"); no TMEM/tcgen05, 99 KiB shared memory per block versus 228 KiB on SM100, so SM100 kernels trap and SM100-sized tiles fail to launch. CUTLASS 3.9 added SM120 block-scaled dense and sparse mainloops; 4.2 added SM120 mixed-input block-scaled grouped GEMM and a blockwise example (87); 4.3 added a MoE grouped-GEMM API. cuBLAS exposes no FP4 GEMM on SM120; Triton `tl.dot_scaled` is a software fallback there.
- **Engines.** FlashInfer `mm_fp4` and its CUTLASS NVFP4 MoE fail on SM120 (issue #2577: cudnn unsupported, cutlass returns zeros, trtllm refuses CC 120; PR #2725 carries SM120 patches). vLLM detects the failure and falls back to **Marlin W4A16** (FP4 → FP16 dequant, no FP4 tensor cores; 40–50% throughput cost; `VLLM_MOE_FORCE_MARLIN=1`), which is why the earlier MXFP4 → Marlin note (#30135) applies to V4.1 experts. CUTLASS #3096 documents the TMA warp-specialized grouped-GEMM failure and a `compute_120f` fix reaching 39 tok/s native FP4 on a 397B MoE across 4 × RTX PRO 6000 (vs 50.5 tok/s on Marlin). TRT-LLM #12706: `TRTLLM_MOE_BACKEND=TRITON` is 6.7× faster than its CUTLASS backend on SM120/121. SGLang 0.5.8 produced NaN on SM120 for that model; `dev-dsv41` on SM120 is only proven by 0xSero's V4.1 run.
- **Speculative decoding interaction.** On the Marlin path MTP acceptance dropped (61–85% vs 89%) and net throughput fell 22%, attributed to draft heads trained on native FP4 activations seeing W4A16-dequantised values. DSpark on our stack will be measured under whichever path E12 finds (E10).
- **Custom kernels in the wild.** chsasank/blackwell: custom CUTLASS NVFP4 GEMM + attention for SM120 in development (GEMM at 38% of peak). VincentKaufmann/fp4-cuda-kernel: CUTLASS 3.8 FP4 GEMM for SM120/121, 143 TFLOP/s, reports that MXFP4 (E2M1 + E8M0) had to be re-quantised to NVFP4 (UE4M3) for the tensor cores. **That claim is a library-version limitation, not a hardware one** (next bullet); CUTLASS 3.8 predates the SM120 block-scaled mainloops (3.9).
- **MXFP4 (UE8M0, block 32) is native on SM120 — verified from source, 2026-09-21.** Three independent confirmations:
  1. *PTX ISA* (docs.nvidia.com/cuda/parallel-thread-execution, `mma` block-scaling section): `mma.sync.aligned.m16n8k64.row.col.kind::mxf4nvf4.block_scale.scale_vec::2X.f32.e2m1.e2m1.f32.ue8m0` is listed for `sm_120a`/`sm_121a`. `scale_vec::2X` over K = 64 is one scale per 32 elements — exactly the checkpoint's UE8M0 g32 layout. The `.kind::mxf4*` variants are arch-specific (`sm_120a`), not part of the `sm_120f` family target.
  2. *CUTLASS atoms* (`include/cute/arch/mma_sm120.hpp`, `SM120::BLOCKSCALED::SM120_16x8x64_TN_VS<VS>`): `VS == 32` emits the UE8M0 `scale_vec::2X` instruction above behind `CUTE_ARCH_MXF4NVF4_2X_UE8M0_MMA_ENABLED`; `VS == 16` emits the UE4M3 `scale_vec::4X` NVFP4 form. `include/cute/arch/config.hpp` enables the 2X UE8M0 form for SM120/SM120a with CUDA ≥ 12.8 (the 4X UE8M0 form needs CUDA 13.1).
  3. *CUTLASS builder* (`include/cutlass/gemm/collective/builders/sm1xx_common.inl`, `detail::blockscaled`): `blockscaled_type<…, cutlass::mx_float4_t<T>>` sets `sf_type = float_ue8m0_t`, `SfVectorSize = 32`; `select_instr()` picks `BlockScaledInstr::MXF4_NVF4` for two 4-bit K-major operands, and its check reads `"MXNV_F4 supports ue8m0 and ue4m3 SF types"`. The SM120 builder (`sm120_blockscaled_mma_builder.inl`) accepts `KernelScheduleAuto`, TMA warp-specialized cooperative/pingpong and the PtrArray (grouped) schedules for this path.
  4. *Shipped test*: `test/unit/gemm/device/sm120_blockscaled_tensorop_gemm/sm120_bs_gemm_mxf4_mxf4_f32_f32.cu` instantiates `ElementPairA/B = cutlass::mx_float4_t<float_e2m1_t>` with `ElementSF = float_ue8m0_t`, `Sm120 + OpClassBlockScaledTensorOp`, RowMajor A × ColumnMajor B (TN), tiles 128×{128,64,32}×256. Sibling grouped tests exist for NVFP4 (`…nvf4_nvf4_f32_bf16_group_gemm.cu`) and mixed `mxf8_mxf4` grouped fusion; no shipped grouped test is mxf4×mxf4, so that instantiation is the one thing E13 stage 1 has to compile and run itself.
  Consequences: (a) the upstream checkpoint's expert weights can feed the tensor cores without re-quantisation, so an E13 kernel is lossless with respect to what DeepSeek trained; (b) the E13 kernel is a **type swap** of example `79d_blackwell_geforce_nvfp4_grouped_gemm.cu` — `nv_float4_t<float_e2m1_t>` → `mx_float4_t<float_e2m1_t>`, `OutputSFVectorSize`/epilogue SF type adjusted or SF-output fusion dropped (we want bf16 D, not FP4 D) — built with `-gencode arch=compute_120a,code=sm_120a`, CUDA ≥ 12.8, CUTLASS ≥ 3.9 (4.x for the grouped SM120 builder); (c) the activation operand A must be block-quantised on the fly too. Two hardware-native choices, both UE8M0 block-32: **W4A4** (`kind::mxf4nvf4`, A as `mx_float4_t`) or **W4A8** (`kind::mxf8f6f4`, A as `mx_float8_t<float_e4m3_t>` × B as `mx_float4_t` — the builder's "Fp4 can be mixed with FP6, Fp8 with MMA.MXF8F6F4" path, the same one example 79c uses for mxfp8 × mxfp6). Which one DeepSeek's own serving kernels use for V4.1 experts is not something we have verified; E13 runs both against a bf16-activation dequant reference and reports the error and speed of each, and Marlin W4A16 stays the accuracy baseline.
- Consequence for this plan: the GPU side of the hybrid (5 ms/token assumed) is a Marlin-path number until E12 measures it, and a native SM120 MXFP4 grouped GEMM (E13) is the one place a custom CUDA kernel could move both the 2-GPU hybrid and the 4-GPU profile.

9. ~~**Does SM120 accept MXFP4 (UE8M0 scales) directly in block-scaled MMA, or only NVFP4 (UE4M3)?**~~ Resolved 2026-09-21 from source (SM120 kernel status, "MXFP4 is native"): yes — PTX `kind::mxf4nvf4 … scale_vec::2X … ue8m0` on `sm_120a`, CUTLASS `mx_float4_t` builder path and a shipped `sm120_bs_gemm_mxf4_mxf4` unit test. 4. **Engram-in-DRAM vs NVMe A/B** has no published data; E9 provides it.
5. **Does `--language-model-only` in vLLM / the SGLang equivalent skip loading the 0.90 GiB vision and 7.39 GiB DSpark tensors?** Changes the resident total by ≤ 8.3 GiB; does not change the 2-GPU verdict.
6. **Engram FP4 (LibertAI) / q3_K quality.** Unevaluated by their authors. Matters for the 2-GPU hybrid, where full FP8 tables in DRAM do not fit (E11).
7. ~~**MXFP4 format mapping.**~~ Resolved for KT 2026-09-21 ("Engine source, verified"): `MXFP4SafeTensorLoader` consumes the upstream packed E2M1 bytes unchanged and only reinterprets UE8M0 scales as BF16 (lossless), so the CPU tier is bit-identical to the GPU tier's weights. llama.cpp's Q4 formats remain a re-quantisation (T3.7).
8. **3-GPU parallelism.** 64 heads / 384 experts do not divide by 3; EP3 with replicated attention or uneven PP are the candidates. Which one sglang-kt or llama.cpp supports decides the 3-card profile.
