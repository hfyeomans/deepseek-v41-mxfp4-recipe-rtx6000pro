# Poteto method research

Scope: research into the AI engineer known as **poteto** and distillation of her method into design input for `recipe-generator/`. Every factual claim carries a markdown URL; all URLs are relisted under Sources. (Companion context: `recipe-factory/README.md` §1–2.)

> **Identity correction (important).** The brief's leads are wrong, verified: `github.com/kznrluk/poteto` is a 404 and `kznrluk` is Kazunari Sasa ([GitHub](https://github.com/kznrluk)); "Sho Kato" matches only an unrelated Apache Spark contributor ([ossrank](https://ossrank.com/c/868457-kato-sho)). poteto is **Lauren Tan** ([GitHub: poteto](https://github.com/poteto), [X: @poteto](https://x.com/poteto)). The handle is the Japanese-style spelling of "potato" — a cute food-related nickname from her gaming days; no source connects her to "Sho Kato" ([Q&A notes](https://blog.hunghg.me/blogs/michelin-kitchen-not-software-factory-poteto-matt-pocock)).

## Skills & Claude-Code methodology

- **pstack mechanics:** `/poteto-mode` matches the task to one of 23 playbooks, opens a todo list whose first items are the playbook steps *copied in verbatim*, and routes to other skills as steps fire ([README](https://raw.githubusercontent.com/cursor/plugins/main/pstack/README.md)). Playbooks include investigation, bug-fix, perf, hillclimb, prototype, eval, babysit, shipping, autopilot-full, autopilot-stack, multi-phase-plan, worktree-cleanup, opening-a-pr ([README](https://raw.githubusercontent.com/cursor/plugins/main/pstack/README.md)).
- **Verification skill — the core.** "The single most important skill": gives the agent hands and eyes — launch, drive, observe, trace ([Barnaby](https://barnabyrobson.org/on-pstack/)). `/create-verification-skill` generates a project-local skill with six sections: **Launch** (exact start command + ready signal), **Doctor** (read-only readiness check), **Drive** (real selectors/commands, no placeholders), **Evidence** (proof from the real user path), **Cleanup** (kill only what you started, never delete evidence), **Helpers** (shipped scripts must be executable, invocation shown). Delivery rule: *"A generated skill that was never executed is a draft, not a deliverable."* ([SKILL.md via Tenten](https://developer.tenten.co/pstack-verification-agent-merge); [Swanky](https://swanky.github.io/technical/poteto-pstack-trust-before-scale/)).
- **Feature Map = materialised memory.** A searchable markdown map of every feature — what it does, how a user reaches it, how to drive it with the CLI, and its traps; saves tokens vs. reading the codebase; needs daily upkeep because the agent trusts it ([Barnaby](https://barnabyrobson.org/on-pstack/)). `/maintain-verification-skill` may fix only the map (outcomes `clean` / `changed` / `blocked`), never the product, to avoid "fixing the spec to match the bug" ([Swanky](https://swanky.github.io/technical/poteto-pstack-trust-before-scale/)).
- **Build the Lever.** Split each task into judgment vs. mechanical parts; move the mechanical part into one small CLI (`doctor`, `snapshot`, `screenshot`, `send`) that every agent reuses, instead of each agent "rebuilding the world each time" ([Barnaby](https://barnabyrobson.org/on-pstack/); [Q&A notes](https://blog.hunghg.me/blogs/michelin-kitchen-not-software-factory-poteto-matt-pocock)).
- **Encode lessons in structure (/correct).** A mistake class counts once it has happened twice; fix at the highest level that works — architecture → types/lint/CI → behavior tests → docs/agent-rules last; every new check must be proven against a real past mistake ([Tenten](https://developer.tenten.co/pstack-verification-agent-merge); [correct SKILL.md](https://github.com/cursor/plugins/blob/main/pstack/skills/correct/SKILL.md)). Dune, her internal "Next.js for Electron apps", operationalizes it: one supported way per task, feature directories, strict lint, process boundaries visible in the tree ([Tenten](https://developer.tenten.co/pstack-verification-agent-merge), [Swanky](https://swanky.github.io/technical/poteto-pstack-trust-before-scale/)).
- **Independent verification.** `autopilot-full`: one owner agent per PR; merge only after an independent verifier swarm returns clean on the *exact* patch (re-verified on every push) and CI passes on the rebased head; the author's own verdict never counts ([playbook](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-full.md); [Tenten](https://developer.tenten.co/pstack-verification-agent-merge)).
- **Overnight contract.** Four parts: goal, finish condition, permissions, escape hatch — "a duration is not a finish condition" ([guide](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/07-overnight.md)).
- **Measurement hygiene.** `/benchmark-checklist` vets any measured number (limiter, tuning, errors, repeat runs, end-to-end relevance) before reporting or acting; principle `explain-the-number`: find what limits the number and rule out measuring the wrong thing ([README](https://raw.githubusercontent.com/cursor/plugins/main/pstack/README.md)).
- **Context engineering.** `/recall` rebuilds a tight current-state brief from history; `guard-the-context-window` routes bulk to subagents, keeps summaries in the main thread; `/why` grades evidence as direct / supporting / inference / guess / unknown ([README](https://raw.githubusercontent.com/cursor/plugins/main/pstack/README.md); [Swanky](https://swanky.github.io/technical/poteto-pstack-trust-before-scale/)). From Netflix, "context, not control": give agents the context to work alone ([Q&A notes](https://blog.hunghg.me/blogs/michelin-kitchen-not-software-factory-poteto-matt-pocock)).
- **Claude Code.** pstack installs natively in Claude Code (`/plugin marketplace add cursor/plugins`; `/plugin install pstack@cursor-plugins`; `/poteto-mode` → `/pstack:poteto-mode`) with an adapter doc mapping every Cursor name ([README](https://raw.githubusercontent.com/cursor/plugins/main/pstack/README.md)); community port [anhermon/pstack-claude](https://github.com/anhermon/pstack-claude). Her methodology is harness-portable markdown skills — not tool-bound.

## Distilled practices → recipe generator

(Table sources: the Skills & Claude-Code methodology section above; every practice is cited there.)

| Poteto practice | What it means | Where it lands in `recipe-generator/` |
|---|---|---|
| Michelin kitchen, not factory ("organize the kitchen, cook less") | The engineer builds the environment once and stays accountable for output; each dish is then cheap | Core stance: budget JSON + hardware JSON + typed knob registry + gate suite are the "prepared kitchen", built before any checkpoint download; generator README vision |
| Trust ladder ("trust before parallelism") | Parallelism is only safe once verification exists and is trusted; more agents early = more exceptions | Agent front-end may not fan out parallel P3 build routes until P2 baseline has qualified on this harness and the feasibility calculator reproduces its calibration point |
| Verification skill = hands and eyes; "never executed = draft" | The agent runs the real thing, drives it, and captures evidence from the real path before anything is called done | Every generated recipe ships a verify path (serve + needles + stamps); qualification exit criteria require an actually-served run stamped in evidence/ — a recipe never served is a draft, not a deliverable |
| Feature Map = materialised memory | One searchable page: what exists, how to drive it, its traps; kept fresh because agents trust it | The one-page map (hardware → tiering → knob → gate) generated per run from evidence JSON; staleness is a failing check, never hand-edited |
| Build the Lever (deterministic → script; judgment → agent) | Mechanical task parts become one tested script every agent reuses; agents keep only judgment | checkpoint-budget / feasibility-calc / bench-* / manifest-stamp scripts are the levers; the front-end agent only judges trade-offs (profile choice, ladder shape) — explicit script-vs-agent boundary |
| Encode lessons in structure (five-layer correction) | Repeated mistake classes move upward: architecture → types/lint/CI → tests → docs last; "the best rules are in your code" | Knob registry as a typed schema that refuses unknown/mistyped/removed/unsafe values at parse time; every gate-caught failure class must land as a schema/check/test before prose — docs are the last resort |
| Gardener (watch → queue → group → change the bed); sampling not blocking | Buffer findings, look for shared causes, fix the environment; sample output instead of reviewing every dish | Tried-options ledger is the queue: periodic review groups rejections by shared assumption and fixes the calculator/gates, not individual recipes; gate-result sampling is the maintainer loop |
| Inner/outer loops; "context, not control" | Give agents the context to work alone; teach them to fetch answers from real data, not the human | Agent front-end answers every question from evidence JSON / hardware map / registry — no human proxying of numbers; new model/bug reports enter as data, not instructions |
| Overnight contract (goal, finish condition, permissions, escape hatch) | A duration is not a finish condition; escape hatches are explicit | Phase briefs use the four-part shape: one exit criterion per phase (already in recipe-factory P0–P4), explicit permissions, documented blocked reason as the escape hatch |
| Independent verification (author never merges on own verdict) | Fresh-eyes verifiers on the exact patch; self-grading is where pipelines break | Gates run by a separate pass from the build agent, pinned to the exact revision + serve-config hash; CI re-runs gates on the final head before publication |
| explain-the-number / benchmark-checklist | Vet every measured number (limiter, tuning, errors, repeat runs, end-to-end relevance) before reporting or acting | Pre-qualification review: no number enters a headline table or profile trade-off without a named limiter and repeat-run/error checks |
| sequence-verifiable-units | Small units, each ending in a verifiable state, checked before the next | Per-phase exits plus per-knob before/after evidence units; delivery ordered so the sequence proves itself |
| prove-it-works / behavior-not-implementation | Verify against the real artifact — not proxies, self-reports, or "it compiles" | Names the existing gates: NLL identity, needles, stress, batch consistency, health, power are behavior gates on a real serve, never config-file assertions |
| attack-the-premise; exhaust-the-design-space | Two fixes sharing a premise fail the same gate → test the premise; build 2–3 competing prototypes | Feasibility calculator's calibration-point rule + ledger rule: two rejected routes sharing one assumption → re-measure the assumption; P3 runs competing routes in parallel under one harness (/arena) |
| recall + guard-the-context-window | Tight current-state brief; bulk to subagents, summaries in the main thread | The one-page map + stamped evidence JSON is the agent's per-model brief; benchmark logs stay in subagent scope, only summaries enter the plan |
| never-block-on-the-human (with permissions) | Proceed and let the human correct after; confirmation reserved for irreversible actions | Auto-proceed on read-only/reversible steps (header reads, microbenches, dry-run recipes); human gates on irreversible ones (downloads, storage-layout commits, publishing) |
| Shape-valid ≠ qualified (check-plan.mjs) | A plan passing a format check is not a verified plan | Recipe descriptor gets a schema lint, but publication requires gate evidence attached — lint alone never qualifies |
| Skills shrink; workflow not commands | As models improve, keep only the workflow; "skills are process written down" | Agent front-end playbooks stay thin, referencing the registry and scripts; recipe templates stay lean and regenerate |

## What this adds beyond recipe-factory

`recipe-factory/` already has methodology with exit criteria, feasibility math before download, microbenchmark-to-decision mapping, gate discipline, a tried-options ledger, a typed knob registry, profiles, and evidence JSONs — structurally it is already poteto-shaped. What her method adds that recipe-factory lacks:

1. **A named doctrine** — the Michelin kitchen gives the generator an identity and defines the owner's role ("chef builds the environment, stays accountable, samples output"); recipe-factory has mechanics but no governing metaphor.
2. **Trust-before-parallelism as an explicit scheduling constraint** for the agent front-end — gates exist, but nothing currently gates *parallelism* on harness trust.
3. **The verification-skill contract** (Launch/Doctor/Drive/Evidence/Cleanup/Helpers) plus the **execute-before-deliver rule** — a concrete, checkable shape for per-recipe verify paths; recipe-factory's evidence discipline lacks the hard "never executed = draft" rule.
4. **The Feature Map + upkeep loop** (clean/changed/blocked outcomes; never fix the product to pass the map) — recipe-factory has no single materialised map artifact with staleness handling.
5. **The five-layer correction order as a standing post-gate loop** — turns ledger rows into structural fixes on a schedule; today the ledger records but does not automatically promote.
6. **Independent-verification doctrine** — gates exist, but recipe-factory does not yet require a distinct verifying pass pinned to the exact artifact (self-grading protection for the agent front-end).
7. **Benchmark vetting checklist** — recipe-factory measures rigorously but has no explicit pre-publication check that each number's limiter is named and confounds ruled out.
8. **The overnight-contract brief shape** — turns phase exit criteria into delegable task briefs with permissions and escape hatches.
9. **Evidence epistemics taxonomy** (measured / inferred / guess / unknown) as a typed field in evidence JSON — strengthens "zero estimate rows" into machine-checkable form.
10. **An anti-pattern warning**: poteto is explicitly anti-plan-doc ("the best spec is code"); keep P0 artifact-driven (budget JSON, calculator) and treat plan documents as *outputs* of the agent front-end, never as gates themselves.
