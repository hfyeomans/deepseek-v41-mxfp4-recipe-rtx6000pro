# Landscape check — placement planning & serving-recipe generation

Date: 2026-10-23. Extends and re-verifies §1 of `recipe-factory/README.md` (the prior same-day survey) with fresh
fetches; nothing below is copied from it unverified. Scope: who plans *where checkpoint components live*
(VRAM / host DRAM+CPU / NVMe), who picks quant and tiering levers, who emits a serving config, and who gates it.

## 3. Does anything already do "budget JSON → tier plan + projections"?

**No.** Nothing takes component budgets + tier capacities + measured bandwidths and emits a multi-tier placement plan
with throughput projections and qualification gates. The honest partials:

| Partial | Does | Missing (why we still build) |
|---|---|---|
| gpu-container | budget→placement (VRAM/pinned/NVMe) + measured receipt + refusal + calibration loop | llama.cpp lane only; no safetensors-header component budgets, no projections before launch, no quality gates (NLL/needle/stress), no profiles/ledger, no Engram/DSpark specifics; beta, one author |
| llama.cpp `--fit on` | budget→GPU/CPU split, automatic | binary split, no projections, no NVMe, no gates |
| SGLang Paged Experts auto-K | budget→K resident experts (GPU/host), byte-exact sizing | no NVMe tier, no projections, no gates, single knob |
| llm-sizer | budget(weights+KV)→cheapest single GPU | single tier, cloud catalog, no placement, no projections |
| EPLB | activation stats→GPU-level expert placement | no memory tiers, no config emission |
| PrefixPlace | KV placement with provable bounds | KV only, not weights/checkpoint components |

Verdict: keep building the placement engine. Watch gpu-container (the only true competitor and its receipt/refusal
semantics are worth copying); watch vLLM RFC #38256 and llama.cpp #27861 (they may ship the runtime tiering we plan
around).

## 4. Borrow-vs-build decisions

| Piece | Borrow (URL → what exactly) | Build (why) |
|---|---|---|
| vLLM recipes schema/provenance | [SCHEMA.md](https://github.com/vllm-project/recipes/blob/main/SCHEMA.md) → meta/model/variants/hardware_overrides/strategy field vocabulary; `ceil(params×B×1.2)` + safetensors-`total_size` mixed-precision correction; `source` (repo/commit/path) provenance; `verified`-per-hardware convention; `/hw/<hardware>.json` API shape. | Our descriptor adds: component budgets, tier assignments, projections, gate results, ledger links — fields vLLM doesn't model. |
| Local AI Registry catalog | [API](https://local-ai-registry.vercel.app/api/v1/index) → normalized hardware×model×recipe records, `validated` flag, evidence linkage. | We publish our recipes there; we keep our own evidence JSON schema (registry has no gate semantics). |
| dynamo find-serving-recipe | [PR #14211](https://github.com/ai-dynamo/dynamo/pull/14211) → tier ladder order, tag-resolvability + freshness gates, immutable SHA256 dossier, conflict precedence. | We add the build/measure/qualify stages it deliberately excludes; use it as our pre-build catalog scan. |
| llama.cpp offload semantics | [PR #11397](https://github.com/ggml-org/llama.cpp/pull/11397), [PR #27861](https://github.com/ggml-org/llama.cpp/pull/27861) → `-ot` regex placement vocabulary; **LRU-over-static hot-list evidence** for expert caching. | Hot-expert maps from our own router stats + LRU residency policy in our tiering engine. |
| Planner math | [FlexGen](https://arxiv.org/abs/2303.06865) → cost-model/LP offload scheduling; [EPLB](https://github.com/deepseek-ai/eplb) → replication + packing over load stats; [PrefixPlace](https://arxiv.org/abs/2608.01655) → facility-location structure; [Paged Experts sizing](https://github.com/sgl-project/sglang/pull/42557) → budget→K from safetensors headers. | Tiering engine on **measured** bandwidths (DRAM read ceiling, NVMe row gather, PCIe additivity), per-component budgets, Engram/NVMe tiering, deferral, projections. None of the borrowed math covers our measured-bandwidth calibration discipline. |
| TensorFold/EXL3 | [ExLlamaV2](https://github.com/turboderp-org/exllamav2) → measurement→per-layer bit-allocation recipe pattern. | Already have (microbench→decision); adopt the artifact shape for quant recipes. |
| gpu-container | [docs](https://mcp-tool-shop-org.github.io/gpu-container/) → receipt-vs-roofline + honest-refusal + calibration feedback semantics. | Our gate discipline (NLL identity, needle ladder, stress, batch consistency) and profile/ledger layers — it has neither. |
| The Forge | [design note](https://al-engr.com/designing-an-inference-recipe-generator.html) → two-loop structure, experiment-card contract, do-not-retry ledger, human gate. | Validates our loop; it has no placement engine, so our core remains the differentiator. |

**Built by us because nobody has it:** budget-JSON input → per-component tier plan + throughput/latency projections;
qualification gates as a mechanical claim; tried-options ledger; profile presets with measured trade-offs;
evidence manifests consumed by a UI. The nearest competitor (gpu-container) proves the niche is real and still open.
