## E22  Layerwise GPU prefill for the CPU-resident experts: what does re-exporting the CPU tier cost, and how fast can prefill get?

- Status: **in progress** 2026-09-23 (GPU window). Owner T3.6b2.
- Question: prefill is 216 tok/s because the 176 CPU experts per layer run on 16 cores for every 4,096-token chunk (E19 item 4). The fork's `_Mxfp4LayerwisePrefillManager` instead streams each layer's CPU experts to the GPUs and runs the MoE there. On SM120 our GPU tier (`Mxfp4FlashinferCutlassMoEMethod`) consumes the checkpoint's raw MXFP4 bytes, so the streamed experts need no Marlin repack  only a gate/up half swap (kt writes `[gate; up]`, SGLang stores `[up; gate]`), a bf16E8M0 scale shift and FlashInfer's `block_scale_interleave`. What bounds the streamed path: kt-kernel's host-side export (`write_weight_scale_to_buffer`, a multithreaded memcpy of  20 MB per expert, 3.5 GB per layer, 113 GiB per chunk), the two x16 links (E4: 53 GiB/s each  1.06 s per chunk), or the GPU GEMMs?
- Hypothesis: the host export is the ceiling, at 4080 GB/s aggregate  4590 ms per layer  1.73.3 s per chunk regardless of chunk size; so (a) streamed prefill lands at 1.22.5K tok/s with 4K chunks, (b) the chunk size becomes the main lever (16K chunks  510K tok/s if activations fit), and (c) the break-even prompt length vs the CPU path is  400700 tokens. The bytes kt exports are checkpoint-identical (librarian, `fp4-moe.hpp`), so streamed-prefill NLL should match the D=0 CPU baseline (1.48741) to  1e-3.
- Procedure:
  1. `scripts/kt-export-bench.py` (E22a, one layer in the recipe image, no server): build the compact 176-expert `KTMoEWrapper` for layer 5 as `test-kt-one-layer.py` does; export every expert for `gpu_tp_count=2` into pinned host buffers; **byte-compare** rank slices against the safetensors shards (weights, `bf16 == e8m0 << 7`, gate/up order, w2 column slicing); time the export (sequential submits, one sync; groups of 8/16/32)  GB/s; time the GPU prep (swap-copy H2D to both cards concurrently + scale shift + `block_scale_interleave`)  per-layer streaming cost with and without write/H2D overlap.
  2. From (1), derive the per-chunk cost and the break-even length; pick the group size and the default `--kt-gpu-prefill-token-threshold`.
  3. Implement the streaming path in the overlay `kt_ep_wrapper.py` (E22b): POSIX-shm pinned host double buffer shared by both TP ranks, per-layer GPU slots, gloo barrier per group, GPU MoE over the compact CPU-expert ids with the existing FlashInfer runner; CPU path kept for chunks under the threshold and for decode.
  4. Serve, `verify.py` 16K, `nll-score.py` vs `nll-d0.json`, `bench-prefill.py` at 16K/32K with chunk sizes 4096/8192/16384 (E22c).
- Pass: (1) byte-identical export; (4) verify all-pass, |NLL| < 0.002 vs D=0, prefill  1,000 tok/s at 16K ( 4.6 E19) with no decode regression (C1  38 tok/s).
- Results, E22a (`evidence/e22-layerwise-prefill/e22a-export-bench-t16.json`, `-t8.json`, `e22a-kernel-check.json`; layer 5, 176 CPU experts, `gpu_tp_count=2`, kt-kernel 0.7.0.post4):
  - **Export is byte-identical** to the shards for compact experts 0, 1, 175 on both ranks (w13 `[gate; up]` rows, w2 column slice, scales `bf16 = e8m0 << 7`). One rank slice is 9.49 MiB per expert (my 9.96 MB estimate was 5 % high: 5.63 + 0.70 + 2.81 + 0.35 MiB); a layer is 3.26 GiB for both ranks.
  - **Export throughput: 67.6 ms per layer = 51.8 GB/s at 16 threads, 121.9 ms = 28.7 GB/s at 8 threads**  linear in threads, so it is core-bound (memcpy + scale conversion per thread  3.2 GB/s), not DRAM-bound. Group size (8/16/32/44 experts per sync) does not matter (6869 ms).
  - H2D of a full layer to both cards concurrently: 36.7 ms (44 GiB/s per card, E4-consistent); + scale shift + interleave 38.4 ms.
  - Pipelined write(g+1)  H2D(g): **8793 ms per layer** (best G=32), i.e. only ~17 ms of the 37 ms H2D hides behind the export; serial would be 104 ms. With 8 export threads 141 ms.
  - **Staged layout == resident layout, bit for bit**, on both ranks (`_StreamedExpertSlots.load()` output vs tensors built the way SGLang's loader builds them: `[up; gate]`, E8M0 uint8, `block_scale_interleave`), and the FlashInfer SM120 fused MoE gives **exactly the same output** on the staged and the resident tensors (max |diff| 0) for 16 tokens  top-6 with one resident id per token masked to 1. Both are 0.0444 rel-L2 from the fp32 dequant reference  that is the GPU tier's existing MXFP8-activation error (kt's CPU path was 0.0038 in T3.6b), not something the streaming adds.
  - Projection (40 MoE layers, all streamed):  3.5 s of streaming per chunk, plus the all-GPU compute of the chunk (~2 s at 16K from the E8 dsv4-nvfp4 prefill rate)  16K chunk  3,000 tok/s, 8K  1,900, 4K  1,100; break-even vs the 216 tok/s CPU path  750 tokens  default threshold 1,024. Hypothesis (a)(c) hold so far; the export, not the links, is the ceiling, and it is the CPU cores.
- E22b implemented in the overlay (`kt_ep_wrapper.py`: `_LayerwisePrefillCoordinator`, `_HostSlice`, `_StreamedExpertSlots`; env `KT_GPU_PREFILL_MIN_TOKENS`, `KT_GPU_PREFILL_LOG`): full-layer granularity, one POSIX-shm pinned double buffer (2  2 ranks  1.63 GiB = 6.5 GiB) created by rank 0 and `cudaHostRegister`ed by both, per-rank GPU staging 1.9 GiB (w13/w2/scales + bf16 landing zone + half-swap scratch), export of layer L+1 submitted right after layer L's GEMM, two gloo barriers per layer (buffer filled; buffer free), DMA on the compute stream (v1: no second staging set), FlashInfer runner called a second time per layer with compact ids. Serving knob in `serve-hybrid.sh`.
