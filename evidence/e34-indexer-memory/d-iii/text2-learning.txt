# Learning guide

A reading map for every piece of this project, written for the owner. Each section says why the piece matters *for this build*, what to read (primary sources first), and where it shows up in this repo so you can connect the reading to a file you can run. Read in order the first time; afterwards jump to whichever experiment you are about to run and read its row in the last table.

Difficulty marks:  background,  working knowledge needed to run and interpret experiments,  needed to write or modify kernels.

## 0. The one-paragraph map

We want a 475 GiB model on 192 GiB of VRAM. The model is a Mixture-of-Experts (MoE): most of its weights are "experts" of which only 6 of 384 fire per token, so weights that are not in VRAM only cost bandwidth when they are used. That turns the problem into memory-hierarchy engineering  VRAM (1.79 TB/s)  host DRAM (~150300 GB/s)  NVMe (~14 GB/s, but 400K random rows/s)  and into kernel engineering, because the tensor cores on our RTX PRO 6000 (SM120) run 4-bit math natively only through a specific instruction that no serving engine uses yet on this card. Everything in `plan/` is one of those two threads.

### 5.1 Why a correct GEMM can run 20 below the roofline: tiles, occupancy, split-K (E20)

E19's profile put 57 % of the V4.1 decode step in one Triton kernel, `_w8a8_block_fp8_matmul`, doing the *dense* FP8 GEMMs (attention projections, shared expert, dense MLPs). Nothing was wrong with it: same math, right answer, tuned on H100/H200. It was 20 slower than the memory system allows. Understanding why is the most transferable lesson in the kernel track, because it is the failure mode of every "it works on H100" kernel on a new GPU.

**The mental model.** A decode GEMM has M = batch (14 tokens), N = output width (1.8K25.6K), K = input width (1.1K6K). The weight matrix is NK bytes of FP8 and must be read once per step; the activations are tiny. So it is a *memory-bound* op and the only question is how many bytes per second the kernel pulls from GDDR7. Roofline: 21 MB (51204096) at 1.6 TB/s  13 s.

**How a tiled GEMM turns that into work.** Triton (and CUTLASS) launch one CTA per (BLOCK_M  BLOCK_N) output tile; each CTA loops over K in BLOCK_K slices, loading an A tile and a B tile per iteration and feeding `tl.dot`. Three knobs decide whether the memory system is kept busy:

1. **Grid size (parallelism).** CTAs in flight = (M/BLOCK_M)  (N/BLOCK_N). With M=1 that is just N/BLOCK_N. The default here was BLOCK_N=32  160 CTAs for N=5120 on a 188-SM card: under one CTA per SM, and each CTA is 4 warps. The profile read this as 23 % occupancy.
2. **Bytes in flight per CTA (pipelining).** Each iteration loads a BLOCK_K  BLOCK_N slice of B  3232 = 1 KB here. `num_stages` is how many iterations are prefetched ahead (software pipelining through shared memory). 160 CTAs  3 stages  1 KB  0.5 MB outstanding. GDDR7 needs several MB outstanding to hide its latency (Little's law: bandwidth  latency  1.6 TB/s  ~600 ns  1 MB minimum, more in practice). The result is a latency-bound serial walk down K.
3. **The K loop length.** K/BLOCK_K iterations, each a dependent step. With BLOCK_K pinned at 32 by the scale layout (below), K=4096 is 128 serial iterations per CTA.

**Why BLOCK_K is stuck at 32.** V4.1-Flash quantises dense weights with a per-(3232)-block FP8 scale (`block_shape=[32, 32]` in the checkpoint's `quantization_config`). The kernel applies the scale once per K-tile (`n_tiles_k_per_group_k = group_k // BLOCK_SIZE_K`), so BLOCK_K must divide 32. DeepSeek-V3 used 128128 blocks, and every tuned config SGLang ships is for 128  which is also why its tuner filters `block_k % BLOCK_SIZE_K == 0` over a `{64, 128}` search space and finds nothing for 32. BLOCK_N is *not* constrained: the kernel indexes the scale per column (`offs_bn // group_n`), so a 64- or 128-wide N tile just reads two or four scale columns.

**The two fixes, and why they are the same fix.** Both raise bytes-in-flight:

- **Split-K.** Launch SPLIT_K CTAs per output tile, each doing K/SPLIT_K of the loop into an FP32 partial buffer, then a reduce kernel sums the partials. Grid 8 at the cost of an 8MN4-byte scratch buffer (trivial at decode M) and one extra small launch. This is what the existing `_w8a8_block_fp8_matmul_hopper` kernel does; SGLang gated it to `is_sm90` only because that is where it was tuned  the kernel is portable Triton with no Hopper intrinsics.
- **SWAP_AB.** For M < 16 the MMA instruction's minimum M tile (16) wastes 15/16 of the A rows. Transposing the problem (compute C = B A) puts the weight's N dimension on the MMA's M axis, so the wide operand fills the instruction and the tiny batch sits on N. Same bytes, fewer wasted MMA lanes, and a larger effective tile per CTA.
- More `num_stages` (45) and fewer warps (2) also help at these sizes: fewer warps per CTA means more CTAs per SM's register/smem budget; more stages means more outstanding loads per CTA.

**How the engine picks a config.** `get_w8a8_block_fp8_configs(N, K, block_n, block_k)` looks for `configs/N=,K=,device_name=<nvidia-smi name with underscores>,dtype=fp8_w8a8,block_shape=[bn, bk].json`; the JSON maps batch sizes to configs and the runtime picks the key nearest to M. No file  the default `{BLOCK_M 64, BLOCK_N block_n, BLOCK_K block_k, 3 stages}` and a one-line warning at rank 0 that is easy to miss in 600 lines of startup log. Two consequences worth remembering: (a) the device name is part of the key, so a config tuned on "RTX PRO 6000 Blackwell Max-Q Workstation Edition" is not found by the non-Max-Q card; (b) the nearest-M lookup means a config file tuned only at small M would hand prefill (M=4096) a decode config  tune both ends.

**How E20 tuned it** (`kernels/e20/tune_w8a8_block32.py`): import SGLang's own kernels, build the search space the stock tuner cannot (BLOCK_M 16, BLOCK_N 16128, SPLIT_K 116, SWAP_AB, 28 warps, 25 stages for M  16; conventional tiles for M  32), time each with `triton.testing.do_bench` (CUDA events, L2 flushed), then check the *winner* against an FP32 dequantised reference before writing it  a fast kernel that silently disagrees is worse than a slow one. Verdict and numbers: E20 in EXPERIMENTS.md.
