# Troubleshooting

## `preflight.sh` fails with "checkpoint does not fit"

This is the expected outcome on two RTX PRO 6000. It is not a configuration problem. The calculator output above the failure line shows the margin (about −112 GiB with Engram in host DRAM). Options: see [FEASIBILITY.md §4](FEASIBILITY.md). To run experiment E5 anyway, set `ALLOW_UNQUALIFIED=1` and expect the container to die during weight load with a CUDA OOM at roughly 140 GiB demanded per GPU.

## Hugepages warning from `preflight.sh`

SGLang's Engram host table (`SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1`) allocates the ~189 GiB FP8 tables in hugepage-backed memory. Reserve at runtime (reversible; fails if memory is fragmented, so do it soon after boot or while nothing large is running):

```bash
# 2 MiB pages: 190 GiB = 97,280 pages
sudo sysctl -w vm.nr_hugepages=97280
grep HugePages_ /proc/meminfo
```

Or at boot in the kernel command line: `hugepagesz=1G hugepages=190`. This host has 246.8 GiB; after 190 GiB of hugepages about 56 GiB remains for the OS and the serving process, which is enough for SGLang's host-side buffers but not for a second large model. Revert with `vm.nr_hugepages=0`.

If the GLM container is running, `docker stop glm53-flash-2x-rtxpro6000` first; it pins host memory.

## SM120 pitfalls reported by the community for DeepSeek-V4 / V4.1

From vLLM issues #47266 and #56700 and the 0xSero SGLang recipe. Not all reproduce on every build; check before applying.

| Symptom | Cause | Mitigation |
|---|---|---|
| Server hangs at startup with no log progress | DeepGEMM / FlashInfer autotune on SM120 | Disable autotune for the affected backend; SGLang cookbook says leave backends on auto |
| Crash during CUDA graph capture | Capture pool exceeds memory or unsupported kernel in graph | `--enforce-eager` (vLLM) / `--disable-cuda-graph` (SGLang); expect lower decode throughput |
| Wrong answers only on prompts ≥ 100K tokens | FP8 KV scale layout bug | Use `KV_CACHE_DTYPE=auto` (BF16) or a build that includes the fix; `verify.py --context 262144` catches it |
| MXFP4 experts run slowly | Marlin fallback instead of native FP4 grouped GEMM (vLLM #30135) | Check the kernel selection in the server log; compare against SGLang's FlashInfer MXFP4 path |
| All-reduce errors or NCCL hang on PCIe boxes | Custom all-reduce on non-NVLink topology | `--disable-custom-all-reduce` (vLLM); confirm `nvidia-smi topo -p2p r` shows OK |
| Sparse MLA dispatch error | FlashInfer SM120 dispatch gap for some head configurations | Use the SGLang preview image, which the 4-GPU recipe proved on SM120 |

## `dsv41-kt` dies at decode graph capture with `ImportError: libnvrtc.so.12`

Seen on the first T3.6d serve (2026-09-21). The traceback ends in `deep_gemm/__init__.py`, reached from `deepseek_v4_backend._fp4_paged_mqa_logits`. The base image (`dev-dsv41`, CUDA 13) is fine; the culprit is `pip install --no-deps kt-kernel==0.7.0.post4`. That wheel vendors ~1,000 files that are not kt-kernel at top level — a cu12 `deep_gemm` (832 files, 139-line `__init__` without `fp8_fp4_paged_mqa_logits`), `sgl_kernel` **0.3.21** (replacing 0.4.6.post1 and its `flashmla_ops`/`spatial_ops` `.so`), `triton_kernels`, `flash_attn_origin`, mscclpp — and `--no-deps` unpacks all of them over the base copies. `kt_kernel` itself imports none of them.

Fix (in `config/Dockerfile.dsv41-kt` since this date): download the wheel, run `config/prune_wheel.py` to keep only `kt_kernel/`, `kt_kernel.libs/` and the dist-info, install the pruned wheel. `config/kt_smoke.py` now fails the build if `sgl_kernel/version.py` ≠ 0.4.6.post1, if `deep_gemm/__init__.py` lacks the function, or if any `deep_gemm/*.so` links `libcudart.so.12`/`libnvrtc.so.12`. Rule for any future `--no-deps` install: list `site-packages` top-level entries before and after and diff them.

Do not "fix" this by installing `sgl-deep-gemm==0.2.0` or by moving the image to CUDA 12 — the base already has the right cu13 deep_gemm; the job is to stop overwriting it.

Runs made on the clobbered image (E17 one-layer test, E18 Engram bench) did not touch `sgl_kernel` or `deep_gemm`, so their numbers stand.

## `dsv41-kt` dies in `deep_gemm.fp8_fp4_paged_mqa_logits` with `deep_gemm_metadata=None`

Second T3.6d blocker (2026-09-21). On SM120 SGLang defaults `SGLANG_FP8_PAGED_MQA_LOGITS_TORCH=1` and `SGLANG_OPT_USE_TILELANG_INDEXER=1` (the torch/TileLang fallbacks for the indexer), but V4.1-Flash's low-ratio indexer calls the FP4 DeepGEMM kernel unconditionally and expects the metadata those fallbacks never build.

Fix: launch with `--enable-deepseek-v4-fp4-indexer` **and** `-e SGLANG_OPT_USE_TILELANG_INDEXER=0 -e SGLANG_FP8_PAGED_MQA_LOGITS_TORCH=0`. The cu13 `deep_gemm` in `dsv41-kt:recipe` runs the FP4 indexer on SM120 fine once it is actually asked to.

## `Unsupported BCG output type: LogitsProcessorOutput` from the breakable decode graph

Third T3.6d blocker. `--cuda-graph-backend-decode breakable` (needed because the Engram `file` lookup is a graph break) copies outputs between graph segments and only knew tensors and containers, not the `LogitsProcessorOutput` dataclass the model returns.

Fix: overlay commit `cd55166a` (`breakable_cuda_graph_backend.py`) recurses into dataclasses. Upstream instead moved logits out of the graph (#40222) and no longer needs `breakable` for Engram; our `file` layout still does, so keep the overlay until the layout is ported onto that design.

## `sparse_mla_sm120_prefill.cu dispatch_dsv4_dual` aborts during the server's warmup prefill

Fourth T3.6d blocker. FlashInfer 0.6.18 compiles the SM120 DSv4 dual-pool prefill kernel only for `extra_page_block_size ∈ {64, 2}`. SGLang pages each compressed KV pool at `page_size // compress_ratio`, so with the default 256-token page the V4.1 pools come out at c1 = 256, c2 = 128, c4 = 64, c128 = 2 — and V4.1's `compress_ratios` (5×0, 20×1, 18×2) means 20 layers hit the unsupported 256 and 18 more the unsupported 128. The decode kernel takes `pbs_extra` at runtime and is unaffected; only prefills with more than 64 query rows (the warmup, every real prompt) crash.

Fix: overlay `cd55166a` in `flash_mla_sm120.py` — when the extra pool's page size is not 64 or 2 and divides by 64, re-page the touched pages to 64 through `_split_kv_pages_to_64(..., buffer_tag="extra")` (the tag keeps a separate cache buffer from the SWA split). Cost: ≈ 2–3 GB per card out of the ≈ 7 GB "available" pool; GPU used went 90 → 93.1 GB per card. A real fix is a FlashInfer build that instantiates 128/256, or running SGLang with `--page-size 64`.

## DSpark on: `illegal memory access` in `dspark_verify.py … breakable_cuda_graph.py replay → seg.replay()` on the first decode after a long prompt

E23 attempts 5–7. Short prompts (≤ 512 tokens) speculate, but with a low accept rate (0.26–0.57) and garbled tool calls; the first target-verify step after a 5,376- or 13,463-token prompt dies with `cudaErrorIllegalAddress` inside the breakable graph replay. `CUDA_LAUNCH_BLOCKING=1` names no kernel because the fault surfaces at graph replay. **Eager mode runs the same prompt correctly** (needles 3/3, accept rate 0.77, tool call parsed), so the graph replay, not the kernels, is wrong.

**Status: fixed 2026-09-23 (overlay `838490a6`) — two independent bugs, both in the CUDA-graph path.** A third, only at four concurrent requests, is the next entry (bug C, kt-kernel). All three share one shape — a captured graph holding a pointer that the eager path later frees — and one diagnostic: log allocations with a `capturing` flag and compare the sizes the graph asked for with the sizes the cache registered.

- **Bug A — wrong tokens / low acceptance in graph mode (accept 0.26–0.57, garbled tool calls; eager 0.77).** Root cause: the model's multi-stream overlap (`alt_streams`) runs inside the captured verify graph and the side-stream work is not ordered against the main stream at replay. `SGLANG_OPT_USE_MULTI_STREAM_OVERLAP=0` restores eager-equivalent output (probe 171 tokens exact, 3-needle verify 7/7, accept ≈ 0.9 on the counting probe, 0.6–0.7 on prose). ~~The recipe passes it through `EXTRA_DOCKER_ENV` for every DSpark launch; the proper fix (gate the overlap off only for spec draft/verify forwards) is T3.9 follow-up work.~~ **Closed in code 2026-09-24 (review C4, overlay `5b531732`):** `arg_groups/dspark_overlap_gate.py`, called from the SM120 block of `model_hook.py`, forces the overlap off whenever `--speculative-algorithm DSPARK` is set on SM120 (log line `DSpark on SM120: multi-stream overlap forced off in code ...` before model load) and raises `OverlapGateError` if the launch env explicitly sets `SGLANG_OPT_USE_MULTI_STREAM_OVERLAP=1`. Plain decode (spec off, the qualified profile) is untouched: it is qualified *with* the overlap on. Both branches verified on a DSpark launch killed before weight load (`evidence/t316-review-intake/c4-overlap-gate/`); 7 CPU tests in `ci.sh`. The finer gate (off only for draft/verify forwards, on for the target decode within a DSpark server) stays open as an optimisation if E23 ever re-opens.
- **Bug B — `cudaErrorIllegalAddress` / Xid 31 in the first attention layer of a verify step, second request or first mixed batch.** Root cause: `_split_kv_pages_to_64` in the overlay's `flash_mla_sm120.py` kept its page mask and split-output buffers as *grow-only* tensors in `get_resources().buffers` and **freed the old tensor on growth**. Warmup only touches the SWA pool (mask N=71), the verify graphs were captured with that pointer baked into the `zero_()` memset and the `_page_mark_kernel`/`_page_split_kernel` launches, and the first real prefill after capture grew the shared mask to N=1093–1206 for the compressed pools. Every replay then wrote the freed block: while the caching allocator reused it the graph-input dump showed `positions`/`out_cache_loc` reading back as int8 page marks (`65792` = bytes `00 01 01 00` = pages 1,2 marked), and once the segment was released the captured write hit unmapped memory. Eager never faults because it always uses the current buffer. Fix: retired buffers stay alive for the process (a graph is self-consistent with the buffer it captured because a pool's page count is static), `reserve_split_buffers()` pre-sizes mask and split buffers from the real pool geometry at backend init (log line `[sm120-split] reserved page-split buffers from pools …`), a grow after capture ~~logs at ERROR~~ **raises `SM120SplitBufferSealedError` once `reserve_split_buffers()` has sealed the key (overlay `9ecd54a6`, 2026-09-24, review C5; the ERROR log remains only for keys the reservation never listed)**, and `_page_mark_kernel` drops indices ≥ pool size. Init log line to look for: `[sm120-split] sealed page-split buffers: mask N=577, split pages={'': 280, 'extra': 2308}` on both ranks, before any capture. If the seal error ever fires, the pool geometry passed to `reserve_split_buffers()` is wrong (a pool changed size after init, or a pool is missing from the list); do not "fix" it by re-enabling growth. Discriminator ladder that got there: layer-granular graph breaks (`SGLANG_BCG_DEBUG_LAYER_BREAKS=all`) put the fault in layer 0 → in-graph index guard (`SGLANG_SM120_IDX_GUARD=1`) counted zero out-of-range indices → graph-input dump (`SGLANG_BCG_DEBUG_INPUTS=1`) showed the page-mark bytes → allocation log with pointers showed the grow after capture. Fixed run: probe/verify pass, C1/C3/C4 512-token matrix completes with zero faults.
- Not the cause (ruled out on the way): attention indices past the pool (guard counted 0), stale `full_to_swa_index_mapping`, kt-kernel buffer overwrite, sampler, MTP heads, Engram. FlashInfer's SM120 sparse-MLA kernel treats negative indices as invalid but has **no upper-bound check** on positive ones, which is why a bad index would have been silent.

Earlier hypothesis tested and falsified (attempt 8): `DeepseekV4AttnBackend.shared_read_ends` returns `IN_REPLAY` for DSpark target-verify on the assumption that "DSPARK verify replays one full (non-breakable) graph", while our recipe runs `--cuda-graph-backend-decode breakable` (the Engram `file` lookup is a graph break), so later segments re-read scheduler-shared buffers (`req_to_token`, KV metadata) after the in-graph marker and the overlap scheduler could rewrite them for the next batch mid-verify. The non-DSpark branch of the same function says `POST_REPLAY` for that reason, so the overlay was changed to return `IN_REPLAY` only when `check_cuda_graph_backend(Phase.DECODE, Backend.BREAKABLE)` is false. **The IMA reproduced unchanged with that fix in place** (attempt 8 log, local `evidence/e23-spec-decode/crash/attempt8-shared-read-fix-still-ima.log`; `*.log` is gitignored), so the early marker is at most a latent race, not this fault. The change is kept because the non-breakable assumption is still wrong for this recipe, but it is not the fix.

Bisect steps that were planned before the fix (kept for the method; `--debug-cuda-graph` was not needed in the end): `EXTRA_SERVER_ARGS="--debug-cuda-graph"` (every op eager, but through the same segmented capture/replay path — separates "kernel inside a replayed segment" from "segment plumbing"); then the target-verify metadata path — the decode runner's `init_forward_metadata_out_graph` / `init_forward_metadata_in_graph` and the verify branch of `deepseek_v4_backend.py` — checking that the per-segment metadata (`seq_lens`, KV indices, the re-paged extra pool from the `_split_kv_pages_to_64` fix) is sized for `bs × (K+1)` tokens after a long prefix, since short prompts survive and long ones fault.

Two traps met on the way:
- `--disable-cuda-graph` is `no_cli` in this fork and, in `arg_groups/cuda_graph_hook.py`, the explicit `--cuda-graph-backend-decode breakable` that `serve-hybrid.sh` always passes wins over both `--disable-cuda-graph` and `--disable-decode-cuda-graph`. To run eager, append `EXTRA_SERVER_ARGS="--cuda-graph-backend-decode disabled"` (argparse last-wins). `--debug-cuda-graph` is the middle ground: every op eager but still through the breakable capture/replay path.
- Eager target-verify on the vision-capable DSV4 model entered `_prepare_mm_embeddings` (TARGET_VERIFY is `is_extend()` and text-only requests still carry a `MultimodalInputs` object) and died with `TypeError: 'NoneType' object is not iterable` in `_count_mm_tokens_in_extend` because a verify batch has no `extend_prefix_lens_cpu`. Overlay fix in `models/deepseek_v4.py`: skip the mm-embedding branch for `is_decode_or_idle()` and `is_target_verify()`, matching the vision check two lines below. Graph mode never saw it because the captured dummy batch has `mm_inputs=None`.

## DSpark on, four concurrent requests: rank 0 dies with `Fatal Python error: Segmentation fault` in `torch/cuda/graphs.py replay` — or Xid 31 `ENGINE CE4 … FAULT_PDE ACCESS_TYPE_VIRT_WRITE @ 0x0`

E23 R1 (K=5, D=4) and R2 (K=5, D=0). C1, C2 and C3 pass; **every C4 run** dies in the target-verify replay, either as a host segfault inside `cuGraphLaunch` (rank 0 only, all worker threads idle, the scheduler thread in `dspark_verify.py run_non_compact → _forward_prepared_verify → decode_cuda_graph_runner.execute → BreakableCUDAGraph.replay → seg.replay()`), or as a copy-engine MMU write fault surfacing later as `CUDA error: unspecified launch failure` in the Engram graph break. `KT_MAX_DEFERRED=0` did not change it (R2), so it is not the deferral path. `SGLANG_BCG_DEBUG_SYNC=1` with the new pre-segment-0 sync passed silently, so the fault is in the graph launch itself, not inherited from the preceding prefill or draft step.

**Status: root-caused and fixed 2026-09-23 (Bug C; kt-kernel, not the overlay).** Patch `config/kt-kernel-patches/0001-experts-base-temp-buffer-lifetime.patch`, applied by `config/Dockerfile.dsv41-kt`; ~~until the image is rebuilt, bind-mount it with `EXTRA_DOCKER_ARGS` (see `scripts/serve-hybrid.sh`)~~ (retired: the image carries patches 0001–0003, and `EXTRA_DOCKER_ARGS` is developer-profile-only since T3.24b — see [Retired workarounds](#retired-workarounds-what-an-old-evidence-readme-or-launch-log-may-still-show)). Evidence `evidence/e23-spec-decode/r3/`.

- **Root cause — a CUDA graph baked kt-kernel's single reusable *temp* pinned buffer, which the next eager call freed.** `kt_kernel/experts_base.py KExpertsCPUBuffer.get_buffer(hidden_states)` keys its pinned host buffers (input, expert ids, weights, output, bsz) and the `output_gpu` tensor on the flattened token count. Sizes listed in `capture_bs` get a permanent entry in `capture_buffers`; any other size shares **one** class-level `temp_buffer`, replaced (and thereby freed) whenever a different size arrives. The check order is `capture_buffers` → `temp_bs` → allocate, so a size that was first requested *before* SGLang called `KTMoEWrapper.set_capture_batch_sizes(...)` is stuck in the temp slot even after it is registered. That is exactly what happens under speculation: the flashinfer AutoTuner dummy forward runs the max verify shape (bs 4 × 6 tokens = **24**) 26 s before the target-verify runner exists, while `capture_bs` is still `[]` (`KT_BUF alloc temp buffer bs=24 (prev temp_bs=0, capture_bs=[], captured=[])`), then the bs=4 verify graph is captured and `get_buffer(24)` returns the temp tuple — the graph bakes its D2H/H2D memcpy nodes and the host-callback task pointers to it — then the bs=3 capture allocates 18 and **replaces the temp**. The final cache reads `captured=[6, 12, 18]`: 24 is missing. Every later bs=4 verify (only C4 reaches it) copies into freed pinned memory: a host segfault when the driver touches the unmapped host pages at launch, or a CE write fault if the copy runs. ~~Spec-off C4 has been stable since E21, consistent with the plain decode runner registering `[1, 2, 3, 4]` before its autotune dummy run (inferred from the code order, not re-verified with the instrumentation).~~ **Corrected 2026-09-23 (same day, after the image rebuild):** the plain spec-off decode graph has the *same* defect at bs=4 — the rebuilt image logs `KT_BUF promote temp buffer bs=4 into capture_buffers (capture_bs=[1, 2, 4])` during capture, so on the unpatched build the bs=4 decode graph was baked to the temp tuple that the first prefill freed. It never crashed because the freed pinned pages stayed mapped in torch's caching host allocator and were recycled by later tuples; it **silently corrupted rows 1–3** instead — see the next entry.
- **Fix 1 (root cause):** when `get_buffer` finds the size in the temp slot *and* in `capture_bs`, promote the exact tuple into `capture_buffers` instead of returning the temp (log line `KT_BUF promote temp buffer bs=24 into capture_buffers`); the final cache is now `[6, 12, 18, 24]`.
- **Fix 2 (defence in depth):** replaced temp buffers are retired behind a `torch.cuda.Event` recorded on the current stream and only dropped once `event.query()` is true (bounded list, oldest synchronised if > 16 pending). kt's eager path is fully stream-asynchronous — `copy_(non_blocking)` D2H → `submit_with_cuda_stream` host callback → CPU experts → H2D — and the C++ tasks hold raw `data_ptr()`s that torch's caching host allocator cannot see, so back-to-back different-size prefills (the R3 log shows 193 → 166 → 132 → 256-token temps seconds apart) could free a buffer the CPU workers were still writing. No crash was attributed to this path, but it is the same class of bug.
- **Verification:** no fix → C4 segfault on the first verify (`r3/k5-d0-nofix-c4-segfault.txt`); with the patch → C4 96/128/128-token probes 3/3 pass at K=5 D=0, then the full K=5 D=4 matrix (`r3/k5-d4-fix.*`), zero Xid in the kernel log. Diagnostic that found it in one launch: log every `get_buffer` allocation with `capture_bs`, the registered keys and `torch.cuda.is_current_stream_capturing()`; the culprit is the size that appears in a capture but never in the registered list.
- **Upstream status:** kt-kernel `main` still has the single temp slot (checked 2026-09-23); issue kvcache-ai/ktransformers#1815 (two RTX PRO 6000, four running requests, SIGSEGV with speculative decoding — "we do not support speculative decoding currently") and #2009 (MTP SIGSEGV in graph replay) are this bug. Candidate PR in `docs/research/OPEN-SOURCE-PLAN.md`.
- Ruled out on the way: deferral (R2), token-count vs C++ scratch limits (`_check_qlen_fits_cpp_buffers` uses `chunked_prefill_size`), overlap-scheduler ordering (pre-segment sync), the SM120 page-split scratch (Bug B, already fixed), a DSpark buffer sized `max_bs` indexed by pool slot (all `max_bs` buffers are indexed by batch position).

## C4 decode drops from ≈ 148 to ≈ 50 tok/s after the bug C patch — and four identical greedy prompts in one batch return four different answers on the old build

**Status: understood 2026-09-23. The patched speed is the correct one; the old C3/C4 speed was the bug.** Evidence `evidence/e23-spec-decode/r3/batch-consistency/` and `r3/decode-patched-*.json`; the doc-wide correction is the "Erratum" section in [BENCHMARKS.md](BENCHMARKS.md).

- **Symptom that started it:** the rebuilt image (`dsv41-kt:recipe`, bug C patch applied) ran C1 at 38.4–39.2 tok/s as before but C4 at 49–51 summed / 45–47 wall instead of the 145–148 / 132 recorded since E19. A/B with the pristine `experts_base.py` bind-mounted over the patched image (`EXTRA_DOCKER_ARGS="-v <pristine>:/opt/sglang/lib/python3.12/site-packages/kt_kernel/experts_base.py:ro"`) restored C4 148 — so the patch, not the rebuild, changed the number. A variant that allocates a fresh permanent tuple at capture instead of promoting the temp was equally slow, so buffer *identity* was not the mechanism. `py-spy` on the TP0 scheduler during C4 decode: 90 % of samples blocked in the Engram eager break's D2H copy (`engram.py _engram_file_rows`), i.e. waiting for the captured segment; zero samples in kt Python — the extra ≈ 53 ms per bs=4 step was inside the graph segment (CPU-expert host callbacks), not Python overhead.
- **Why the old build was fast:** the unpatched bs=4 decode graph's memcpy nodes and host-callback task pointers referenced the freed temp tuple. The C++ task reads the batch size and the expert ids through those raw pointers; after the first prefill recycled the pages, the bs=4 graph computed CPU experts for effectively one row and copied stale bytes for the rest — so its step time equalled a bs=1 step, which is exactly the "near-linear batching" the recipe reported. Same-prompt vs distinct-prompt C4 "costing the same" (E19 item 3) was the same bug.
- **Correctness test (new gate, `scripts/verify-batch-consistency.py --same-prompt`):** four identical greedy prompts submitted together (temperature 0, one bs=4 batch); rows must come back byte-identical, or at least share hundreds of characters (rows admitted at different steps see a different batch composition for their first tokens — legitimate drift, typically ≥ 200 chars). Pristine build, C4: row 0 matches the bs=1 reference for 502/509 chars, rows 1–2 diverge at char 16 with a different (still fluent) essay, row 3 answers `The phrase "Explain" is incomplete and lacks context` — it lost the prompt (`batch-consistency/pristine-same-c4.json`). Pristine C3: rows 1–2 diverge at char 16 (bs=3 pads into the bs=4 graph). Pristine C2: both rows correct (bs=2 had a permanent buffer). Patched image: C3 rows byte-identical, C4 min pairwise prefix 225 chars (`patched-same-c3.json`, `patched-same-c4.json`). The E19 "greedy 12-token logprob check at bs=4" that passed compared only the first stream — row 0, the one row the bug computed correctly.
- **What the correct speed says about the CPU tier:** patched image, D=4, 256 tokens, distinct prompts, 3 runs: C1 39.2 summed / 34.0 wall, C2 44.9 / 40.6, C3 38.3 / 35.8, C4 50.8 / 47.0 (`r3/decode-patched-c1234.json`). Step time ≈ 8 ms + 17.7 ms × rows. Same-prompt C4 (all rows route to the same experts) is 56.2 / 49.6 — only 11 % faster than distinct — so kt's CPU cost is per (token, expert) evaluation, not per distinct expert's weight bytes: at M ≤ 4 the MXFP4 CPU kernel does not amortise weight reads across rows. Batching is worth ≈ +30 % aggregate at C4 for a 3× lower per-stream rate; C3 loses to C2 because it pads to the bs=4 graph.
- **Rules that come out of it:** (1) every captured batch size gets the same-prompt gate before a number is recorded (TASKS standing rules); (2) any scaling result that is *better* than the cost model predicts is a bug signal first, a discovery second; (3) quality gates (`nll-score.py`, `verify.py`) run at bs=1 and cannot see a row-2..N defect — do not read a passing NLL as evidence about concurrency.

## `NGRAM=1` passes every gate but emits a token the model itself scores at −20 nats (a seventh `|---` in a six-column table), or the review prompt reads 8+ decode-vs-teacher-forced flips

**Status: known, not fixed (T3.9h-b / E43, 2026-10-12). The `NGRAM` knob is not recommended; the fix is T3.9h-c.** Evidence `evidence/t39hb/`.

- **Symptom:** with `NGRAM=1` (chain-only verify, patch 0059) and a cold n-gram corpus (accept 1.1–1.8), `scripts/spec-consistency.py --flush-cache` reports copy-table 383 / 384 with a 20.5-nat gap at output position 20, review ≈ 354 / 384 with 8 flips > 0.5 nats, long12000 ≈ 368 / 384 with 6. Spec-off reads 384 / 384, 1 and 1 (max gap 0.75 nats). NLL, `greedy-drift.py` and the needles pass on both serves.
- **Why the gates miss it:** `nll-score.py` scores under teacher forcing (no draft is ever rejected), `greedy-drift.py` compares the serve with itself, and the needle gate only needs the right answer somewhere in the output. The defect needs a rejected draft row in the previous step; a warm corpus (accept ≈ 5) hides it (384 / 384, max |Δlogp| 0.000).
- **What is excluded:** CUDA-graph replay (`SGLANG_BCG_DEBUG_EAGER=target` reproduces it bit-identically — note `=1` is a silent no-op, the overlay reads `draft|target`), the multi-stream overlap (forced off on SM120 with NGRAM), the kt CPU tier (bit-reproducible, E38), the offline C128 ring (cleared), the online C128 path (off).
- **Where to look (T3.9h-c):** `deepseek_v4_backend.py` raw-verify path — the c4 indexer compress states and index-k store written for rejected rows (`_low_ratio_compress_torch(..., fuse_index_store=True)`), the SWA paged ring (`storage=paged` under NGRAM) for rejected positions, `seq_lens` vs the accepted length when only the bonus token is kept; diff against DSpark's verify, which never calls the C128 clear and measured ≤ 0.6 nats in E23.

## One request returns HTTP 500 `non-finite logits (NaN/Inf) were produced for this request; it was aborted, the server keeps serving` (err_type `NonFiniteLogits`)

## `dsv41-kt` dies at decode graph capture with `operation not permitted when stream is capturing` from `kt_ep_wrapper.py … _nan_probe`

The same rule applies to any new debug hook in the kt path: nothing that syncs the host may run under capture (T3.16a).

## `AssertionError: KT_BUF capturing unregistered kt buffer size …` / `KT_BUF temporary allocation during CUDA graph capture` at launch

**Since** image rebuild 2026-09-24 (kt patch `0002-experts-base-capture-assertions.patch`, T3.16a). Not seen on the defaults; this is the fail-fast that replaces bug C's replay-time segfault / Xid 31. The message lists `capture_bs` (registered), `cached` (permanently owned tuples) and `temp_bs`.

- *unregistered size*: a graph runner is capturing a token count kt was never told about. With speculation on, the count is `bs × (K+1)`; check the `KT_BUF capture sizes registered: requested=… now=…` lines — every runner's sizes must appear in `now`. If a runner registers after another has captured, the merge in `set_capture_batch_sizes` keeps the earlier sizes; if it does not register at all, that is an overlay bug in that runner's `__init__`.
- *temporary allocation during capture*: the size is registered but no eager warmup ran at that size before capture, so the first request under capture would allocate. SGLang warms each size before capturing it; if this fires, the warmup and the capture disagree on the token count (padding / `captured_req_width`), which is the thing to fix — do not bypass the assert.
- `KT_BUF promote temp buffer bs=N` (a warning, not an assert) means N was requested *before* registration and lived in the temp slot; the patch promotes it. Harmless, but it is the bug-C shape. **Since 2026-09-24 (T3.16c, overlay `8ad514ed`) it should never appear on a healthy launch:** `capture_cuda_graphs` registers the decode/verify token counts before the eager runner's FlashInfer-autotune forward, so the first `KT_BUF capture sizes registered … previously=[]` line precedes `FlashInfer autotune completed`, the decode runner's re-registration shows `cached=[<max_bs>]`, and `KT_BUF post-capture: captured=… registered=… cached=…` on the kt rank lists every captured size under `cached`. A `promote` line after this date means some new forward path (a new runner, a changed `captured_req_width`) requests a kt size before `capture_cuda_graphs` — register it there, do not silence the warning.
- `KT_BUF captured token counts […] were never registered` / `have no graph-owned kt buffer` (asserts at the end of decode capture, T3.16c): the runner captured a size that `kt_capture_token_sizes()` in `cuda_graph_setup.py` did not predict — the two compute the width differently (speculative `decode_num_tokens_per_req`, adaptive draft counts). Make them agree; the assert is the contract.

## Server exits with `torch.OutOfMemoryError` inside `input_logprob_processor._forward_by_chunk` on a `return_logprob` request

**Seen** twice in E29 (2026-09-24) at `KT_NUM_GPU_EXPERTS=230` / `CHUNKED_PREFILL_SIZE=2048` / `MEM_FRACTION_STATIC=0.975`, once after the 4 × 30K stress run and once on a fresh server; never at the 226 default. The log shows an allocation of 1,059,061,760 bytes (= 2048 × 129,280 vocab × fp32) plus a 530 MB bf16 copy with 0.3–0.8 GB free, then `Scheduler hit an exception` → `kill_process_tree` — the **server** exits; the client sees a dropped connection, not a 4xx/5xx.

Why: SGLang scores input logprobs (what `scripts/nll-score.py` and any `logprob`-requesting client trigger) by running the LM head over `SGLANG_LOGPROB_CHUNK_SIZE` prompt tokens at a time and keeping the full-vocab fp32 logits for the chunk. At the default 2048 that is the largest single tensor the served hybrid ever allocates — larger than anything the 4 × 30K decode worst case produces — so a config that passes `stress-kv-full.py` can still die here.

Fix: `serve-hybrid.sh` now sets `SGLANG_LOGPROB_CHUNK_SIZE=512` by default (overlay `srt/environ.py`, used by `srt/layers/logprob_processor.py`). E29 G measured it bit-identical to 2048 on all 4,795 NLL tokens (Δ 0.0) with no material end-to-end change (fresh 25.3 s vs 28.9 s; warm 10.6 s vs 7.3 s). If it still fires, the config has no headroom: lower `KT_NUM_GPU_EXPERTS` (226 → 222) rather than the chunk. The fit gate for any placement/chunk change is `stress-kv-full.py` **then** `nll-score.py` on the same server, in that order.

## `KTContractError: layer N: …` at weight load, graph capture, or the first forward

**Since** 2026-09-24 (T3.16d, overlay `b93cb915`). `sglang/srt/layers/moe/kt_contract.py` is the written-down SGLang→kt-kernel contract; it raises instead of letting kt's pinned staging buffers cast silently or letting a mis-sized TP group return zeros for the CPU tier. Two entry points, both metadata-only (no device sync, so they run under CUDA-graph capture):

- `check_moe_topology` — once per MoE layer at the end of `process_weights_after_loading`. Messages and what they mean:
  - `moe_ep_size=N: the contiguous GPU/CPU expert split …` — expert parallelism was enabled (`--ep-size > 1`). The hybrid assumes every rank sees every expert index; run TP only.
  - `MoE TP group (rank a/b) differs from the model TP group (rank c/d)` — `--moe-tp-size`/dense-TP overrides split the MoE differently from attention. Ranks ≠ 0 return zeros for the CPU tier and rely on the TP all-reduce to fill them in; that only holds when the two groups coincide.
  - `kt wrapper present=… on tp_rank=…; exactly rank 0 …` — the CPU tier was built on a rank other than 0, or not built on rank 0. This is the rank-0 ownership invariant (review C9); until T3.22 lands a rank-balanced design, any other topology is unsupported.
  - `num_gpu_experts=N must be in [0, 384)` — `KT_NUM_GPU_EXPERTS` ≥ the model's expert count (no CPU tier left) or negative. Use `serve-hybrid.sh`, which already caps it at the qualified 226.
  - `max_deferred_experts_per_token=D must be in [0, top_k=6)` — `KT_MAX_DEFERRED ≥ 6` would defer every routed expert. `serve-hybrid.sh` refuses ≥ 5 first; this is the backstop if it is bypassed.
  - `KT_B2_UVA_EXPERTS=n must be in (0, num_cpu)` / `… needs the streamed-prefill export path` — B2 (off by default, rejected in E30) was enabled with a subset larger than the CPU tier, or without the streamer it aliases. Set `KT_B2_UVA_EXPERTS=0`.
- `check_moe_boundary` — at the top of every `apply`, every rank. Messages:
  - `hidden_states (…) must be [tokens, 5120]` / `empty forward (0 tokens)` — a caller flattened or batched the hidden states differently from the fused-MoE convention, or an empty batch reached the MoE. Neither has happened on the recipe launch; if it does, the traceback names the forward mode (decode graph, verify graph, streamed prefill) that produced it.
  - `topk_ids (…) must be [tokens, 6]` / `topk_weights (…)` — router output width ≠ `top_k`, usually a speculative-verify batch whose row count was not rescaled (E23 R1 territory).
  - `topk_ids dtype … must be int32 or int64` / `topk_weights dtype … must be floating point` / `hidden_states dtype … must be bfloat16` — kt-kernel's `input_tensor_cpu` is hardcoded bf16, ids long, weights fp32; anything else would be converted per step by `copy_` with no log line. If you changed `--dtype`, the hybrid does not support it.
  - `… is not contiguous` — a sliced or transposed view reached the boundary; the non-blocking pinned copy would read the wrong bytes. Call `.contiguous()` at the producer, not here.
  - `… on cuda:1 but hidden_states on cuda:0` — mixed devices in one rank's forward; a TP-placement bug upstream of the MoE.

Verify the contract itself without a GPU: `bash scripts/tests/run-kt-contract-tests.sh` (14 tests, each flips one value from the qualified config). Served on the recipe defaults the contract has never fired; the T3.16d gate showed C1 39.63 wall vs 39.86 control and a bit-identical NLL, so it costs nothing to leave on.

## The same prompt at temperature 0 gives a different answer on the next run

Not expected on the launcher default since 2026-10-11: greedy decode is bit-identical run to run (`python3 scripts/greedy-drift.py --output /tmp/drift.json` prints `identical=True` for every prompt). The drift was two run-dependent GPU reduction orders (T3.15b / E38): the FlashInfer fused-MoE finalize, and the indexer top-k order once the request is longer than 512 tokens. Both now have registry knobs that default to the deterministic side — `SGLANG_FLASHINFER_MOE_FUSED_FINALIZE=0` and `SGLANG_DSV41_SORT_DECODE_TOPK=1` (overlay patches 0053 / 0054) — qualified twice in T3.15c and re-measured on the plain launcher in `evidence/t315c/default-flip/`. If you see the drift again, check the serve's `resolved:` line for `fused_finalize=0 sort_decode_topk=1`; an older launcher or an explicit override is the cause. The pre-flip behaviour (the upstream default) is one override away:

```bash
SGLANG_FLASHINFER_MOE_FUSED_FINALIZE=1 SGLANG_DSV41_SORT_DECODE_TOPK=0 bash scripts/serve-hybrid.sh
```

Measured cost 0 (C1 61.0 / 58.1 / 57.5, C4 123.5 / 121.9 / 121.1 over three serves, prefill in band); the corpus NLL moves by −0.0003 nats/token vs the pre-flip anchor because the unfused finalize is a different reduction, not a worse one, and it is bit-stable across serves. One residual stays (T3.15e): past roughly 14K prompt tokens `greedy-drift.py` can print `identical=True … bitwise=False` on a minority of repeats — same tokens, logprobs differ from one decode step on. It is not the levers failing, and since 2026-10-11 it is not the DSV4 top-k kernel either: that kernel's tie-break by `atomicAdd` arrival order was real (`evidence/t315c/offline/`, upstream sgl-project/sglang #35257) and is fixed in patch 0055 (`evidence/t315d/`), but the residual survived the fix and the decode indexer logits replay bit-identically. The source is known since T3.15e (E42, `evidence/t315e/`): at that step one indexer layer's row holds an exact fp32 score tie at its #512 / #513 top-k boundary, and in production one TP rank resolves it the other way on a minority of repeats (the same row through the same kernel offline never flips). The bound is one tied KV position in one layer at one step: logprobs move by ≤ 0.05, the argmax never has. Diagnose a new residual with the opt-in recorder: `PROFILE=developer EXTRA_DOCKER_ARGS="-v $PWD/fp:/fp" SGLANG_DSV41_STEP_FINGERPRINT_DIR=/fp bash scripts/serve-hybrid.sh`, repeat the prompt, then `python3 scripts/fingerprint-diff.py fp` names the first differing (step, layer, stage). Host runtime since 2026-10-11: docker 29.9.0 / containerd v2.4.1 (an `apt upgrade` mid-serve restarts the container runtime and kills a running serve — the symptom is a clean `docker kill` in the launch log with no server error).

## Using the server from a coding agent (OMP, Amp, any OpenAI-compatible client)

The server is a plain OpenAI-compatible endpoint: `http://127.0.0.1:8000/v1`, model `dsv41-flash-hybrid`, no key unless the serve was launched with `API_KEY_FILE` (then `Authorization: Bearer <file content>`). Context is whatever rung you launched (262K × 4 default since 2026-10-11; `CONTEXT_LENGTH=65536` for 64K × 4), so tell the client the same number or it will pack prompts the server refuses. Reasoning is on by default (previous entry): a coding-agent client should either send `chat_template_kwargs: {"thinking": false}` or expect `reasoning_content` in the stream.

OMP (`omp`, oh-my-pi) — add to `~/.omp/agent/models.yml` under `providers:` (explicit entries win over `/v1/models` discovery, which is how the context window and the DeepSeek reasoning field get set):

```yaml
  sglang-dsv41:
    baseUrl: http://127.0.0.1:8000/v1
    api: openai-completions
    auth: none
    models:
      - id: dsv41-flash-hybrid
        name: DeepSeek-V4.1-Flash hybrid (local SGLang)
        contextWindow: 262144      # match CONTEXT_LENGTH of the running serve (262144 at the default rung since T3.46)
        maxTokens: 32768
        reasoning: true
        compat:
          thinkingFormat: openai
          reasoningContentField: reasoning_content
          maxTokensField: max_tokens
          stripDeepseekSpecialTokens: true
          supportsUsageInStreaming: true
```

`auth: none` is for an unkeyed serve. When the serve was launched with `API_KEY_FILE` (any serve exposed through a tunnel), replace that line with `apiKey: "<contents of the key file>"` — OMP's validator accepts either — or every call, including the `/v1/models` discovery, comes back 401 "not authorized". OMP sends `maxTokens` (32,768 above) as `max_tokens`, so the 0051 clamp never triggers for it and the prompt room is the full context minus 32K. Do not also add a `modelOverrides:` entry for the same id: that map patches models *discovered* from `/v1/models`, and with an explicit `models:` entry it is redundant. Measured 2026-10-11 with four OMP agents on the 262K × 4 serve: 183 requests, aggregate decode 121 tok/s at 4 running (56.8 at 1).

Then `omp --model sglang-dsv41/dsv41-flash-hybrid`, and for client-side latency numbers that do not touch the recipe's scripts: `omp bench sglang-dsv41/dsv41-flash-hybrid --detailed --par 4` (TTFT and tok/s p50 / p95, single-user vs 4 concurrent, prefill phase) and `--cache --cache-pairs 3` (cold / warm prompt-cache pairs through SGLang's radix cache). These are a second opinion from outside the container; the recipe's own numbers stay `bench-decode.py` / `bench-prefill.py` because they stamp the manifest.

Amp — a Custom URL model-provider connection (`chat-completions` format) gives a thread the served model with per-thread usage (input / output / cached tokens), tool calls and timings visible in the thread, which is why T3.35 runs through Amp. Two things the OMP route does not need: **Amp's servers make the request, so `127.0.0.1:8000` is not reachable** — expose the port over HTTPS first (`tailscale funnel 8000` on this box, or any tunnel) and launch the serve with an API key the tunnel's callers must present; and the mapping names a canonical Amp model that the custom endpoint stands in for, e.g. `openai/gpt-5.6 -> dsv41-flash-hybrid` (the thread selects that canonical model; the connection rewrites the id). The key is the `API_KEY_FILE` knob (T3.35): `API_KEY_FILE=~/.config/dsv41/api-key CONTEXT_LENGTH=262144 bash scripts/serve-hybrid.sh` passes the file's content as `--api-key`; the manifest and the `resolved:` line record the path only, `--print` redacts the flag. Export the same `API_KEY_FILE` in the shell that runs the evidence scripts — every one of them (and `release-smoke.sh`) sends `Authorization: Bearer` through `openai_client.auth_headers()`; SGLang exempts only `/health*` and `/metrics`, so a bare `curl /v1/models` returning 401 on a keyed serve is the expected shape, not a fault.

What the T3.35 run itself taught (2026-10-10, `evidence/t335/`):

- **A coding agent's fixed completion ceiling shrinks the usable context.** Amp sends `max_completion_tokens: 128000` on every turn; stock SGLang rejects any request whose prompt + that ceiling exceeds `--context-length`, so a 262,144-token serve returned HTTP 400 (`Requested token count exceeds the model's maximum context length`) for every thread past 134,144 input tokens — one of the four concurrent review threads never produced a turn, another was force-compacted by the harness at 140K. Since overlay patch 0051 the launcher sets `SGLANG_DSV41_CLAMP_MAX_NEW_TOKENS=1`: the tokenizer manager clamps `max_new_tokens` to the remaining room (the same bound the scheduler applies anyway) and logs `max_new_tokens 128000 clamped to …`; prompts at or over the context length are still refused. Set it to `0` for the stock 400. The clamp only moves the wall: on the re-run one thread grew to 262,282 input tokens without the harness compacting and then hit the genuine over-length 400, from which no turn (including compaction) can recover — make sure the provider mapping declares the real window and keep review briefs bounded. Do not reach for `--allow-auto-truncate`, which also silently truncates over-length *prompts*.
- **Funnel takes minutes to become reachable, not seconds.** After `tailscale funnel --bg 8000` the public `https://<host>.<tailnet>.ts.net` needed ~14 min for its A record to resolve from outside; the Let's Encrypt cert is only requested on first HTTPS hit and can hit the per-domain rate limit (wait, then `tailscale funnel reset` and re-add). `tailscale serve status` shows the mapping; `curl -sS https://<host>.<tailnet>.ts.net/health` from the box proves the whole path. Tear down afterwards: `tailscale funnel --https=443 off`.
- **Amp's key goes in through the CLI, not the settings tool:** `amp config model-providers edit-router <connection-id> --api-key-file ~/.config/dsv41/api-key`; `amp config model-providers test <id>` must return 200 before any thread is started. A connection's extra headers cannot carry `Authorization`.
- **Throughput and cost of a review turn.** C1 (one thread, 80 requests, context 66K → 152K with one compaction): prefix-cache hit 92 % (6.06 M cached vs 0.51 M new prompt tokens), decode median 55.8 tok/s (p10 51.4, p90 58.5), ~118K output tokens incl. reasoning, 43 min wall of which ~35 min was decode — the review is decode-bound, so a long turn is ~1,500 tokens of visible + hidden reasoning. C4 (four threads at once, 198 requests, 187 × 200 / 11 × 400): cache hit 89 %, aggregate decode 85 tok/s at 2 running, 107 at 3, 124 at 4 (31 tok/s per thread at 4), TTFB median 9 s / p90 15 s, 70 min wall; GPUs at 193–205 W busy-median, 85 °C max, no thermal throttling. A full-repository review therefore costs about one GPU-hour either way; four at once is ~2.2× the throughput of one.
- **Cancelling in the client frees the slot only if the client closes the HTTP connection.** Measured 2026-10-11 (T3.44, `evidence/t344/`): four concurrent streaming requests with ~38.7K-token prompts and `max_tokens 2048`; client 0 closed its socket after 40 streamed tokens and the scheduler's `#running-req` went 4 → 3 on the next decode batch (0.2 s), stayed 3 while the other three ran to `finish_reason: length`, with no abort line in the log (stock SGLang: the streaming response's background task calls `abort_request` ~2 s after the connection ends; non-streaming requests are polled for disconnect). So an interrupted agent holds a quarter of the server only when its harness keeps the connection open after "stop" — a client that merely stops reading the stream, or cancels at the next turn boundary, keeps the slot busy until `max_tokens` (32K for OMP, 128K-clamped for Amp). Re-check with `python3 scripts/verify-disconnect-abort.py --output <dir>/disconnect.json` (needs a running 4-slot serve; exit 1 if the slot is not freed within 10 s).

## Prefill runs at ~200 W per GPU and the 262K×4 stress takes 320 s instead of 260 s (T3.10, `evidence/t310/`)

The weight loader reads all 48 shards (475 GiB) through the page cache. After the load, ~73 GiB of those pages (the dense/attention/MoE tensors that now live in VRAM and are never read again) stay cached and pin the Engram tables to ~10 GiB of page cache, so every first-touched token pays a 4 KiB NVMe read. Check with `fincore` on the shard files (needs `util-linux`): a healthy server shows the Engram-bearing shards cached and the rest at 0. `wait-ready.py` drops the stale shard pages with `posix_fadvise(DONTNEED)` as soon as `/health` answers and prints `dropped … non-Engram shards`; pass `--keep-shard-cache` to opt out. Real text touches about one 264 B row per 4 KiB page (~190 KiB of page cache per first-touched token); the 262K×4 smoke touches 75.6 GiB and gets 38 % LRU hits at 16 GiB of free cache, 55 % at 86 GiB. The drop took prefill 16K from 3,311 to 4,248 tok/s and the stress from 320 to 257 s (`evidence/t310/default-wait-ready/`). Cold vs warm Engram costs a flat +1.7–3.1 s per request regardless of prompt length (`bench-engram-warmth.py`).

## The first long request after a serve takes ~20 s longer than the second

Not Engram: the overlay logs `Triton kernel '_hc_mix_reduce_sinkhorn_kernel' took 13.8 s to compile` plus a lazy "dedicated runner for 165 experts" and about twelve kernel device-loads during the first prefill, all on the container's ephemeral `/root/.cache/sglang` (Triton, nvrtc, DeepGEMM, FlashInfer autotune, inductor). Two fixes ship by default: `serve-hybrid.sh` mounts `KERNEL_CACHE_DIR` (default `~/.cache/dsv41-recipe/kernel-cache`) on `/root/.cache/sglang`, so the second serve starts warm (`KERNEL_CACHE_DIR=` disables the mount), and `wait-ready.py` sends one synthetic chunk+1,000-token prefill after the shard drop (`primed: 9,192-token prefill … ttft=…`; `--no-prime` to skip). The container writes the cache as root; clear it with `docker run --rm -v ~/.cache/dsv41-recipe/kernel-cache:/c alpine sh -c 'rm -rf /c/*'`. Measured: prime TTFT 22.3 s on an empty cache (the compile lands inside it), 7.3 s on a warm one; the warm-cache serve also reached ready in 3m36 instead of 5m04 (capture/warmup JIT) and its ready probe answered in 0.23 s instead of 13.9 s; the first user request afterwards costs the cold-Engram delta only — 7.8 s for a 16K real-text prompt instead of 23.8–25.1 s (`evidence/t310/prime-serve-{a,b}/`). New prompt lengths can still device-load a `_w8a8_block_fp8_matmul` tile config (sub-second, logged as a warning, no OOM observed at 0.16 GiB free).

## Weight load is slow

475 GiB from NVMe at ~14 GB/s is at least 33 s of pure I/O; the engine's dequant and layout passes dominate, and the Engram host-table copy adds a pass over 189 GiB. Ten to thirty minutes is normal on the 4-GPU profile. `wait-ready.py` defaults to a one-hour timeout.

## `download-model.sh` refuses to start

It needs ~500 GiB free at `MODEL_DIR`. On this host nvme0 has 1.7 TB free; make sure `MODEL_DIR` is on it and not on a smaller volume. The checkpoint interleaves vision, DSpark and text tensors across all 48 shards, so a partial download cannot save space.

## `FAIL evidence manifest: …` from a benchmark script, or `ci.sh` says a stamped file does not match its `manifest.json`

Since T3.19f every `bench-decode.py` / `bench-prefill.py` / `nll-score.py` / `verify-batch-consistency.py` / `stress-kv-full.py` run stamps its output with the hash of the manifest the launcher wrote for the running serve (`MANIFEST_DIR/current.json`, default `~/.cache/dsv41-recipe/manifests/`).

- *no manifest at …*: the server was not started through `scripts/serve-hybrid.sh` (or `MANIFEST_DIR` differs). Serve through the launcher, point `EVIDENCE_MANIFEST=<path>` at the right file, or set `EVIDENCE_MANIFEST=none` to record an unmanifested run on purpose (the JSON then says so).
- *describes container X but … is now a different container*: `current.json` is from an earlier serve and the container was restarted by hand. Serve through the launcher again, or `EVIDENCE_MANIFEST_ALLOW_STALE=1` if you really mean this manifest (the stamp records `allowed_stale`).
- *… is a different manifest; one evidence directory holds one serve*: you are writing a second serve's results into a directory that already has a `manifest.json`. Use a new directory per serve.
- *content hash does not match its body*: the manifest or the sibling copy was edited after writing. The redaction `sed` over an evidence dir is safe only because the manifest never contains what it rewrites (it stores `$HOME` as `~`, no bridge IPs); a mismatch means a real edit — re-run rather than patching the hash.
- `python3 scripts/evidence_manifest.py show` prints the current manifest; `verify PATH` recomputes the hash; `check-evidence evidence/` is what CI runs.

## `ci.sh` reports "possible identifier or secret"

The scan catches home paths, LAN addresses, GPU UUIDs, PCI bus IDs and token-shaped strings in tracked files. Scrub the file (replace with placeholders) rather than whitelisting it; evidence JSON is meant to be publishable.
