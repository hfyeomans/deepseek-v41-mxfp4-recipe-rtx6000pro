# Troubleshooting

## `preflight.sh` fails with "checkpoint does not fit"

This is the expected outcome on two RTX PRO 6000. It is not a configuration problem. The calculator output above the failure line shows the margin (about −112 GiB with Engram in host DRAM). Options: see [FEASIBILITY.md §4](FEASIBILITY.md). To run experiment E5 anyway, set `ALLOW_UNQUALIFIED=1` and expect the container to die during weight load with a CUDA OOM at roughly 140 GiB demanded per GPU.

## Hugepages warning from `preflight.sh`

SGLang's Engram host table (`SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1`) allocates the ~189 GiB FP8 tables in hugepage-backed memory. Reserve at runtime (reversible; fails if memory is fragmented, so do it soon after boot or while nothing large is running):

```bash
# 2 MiB pages: 190 GiB = 97,280 pages
sudo sysctl -w vm.nr_hugepages=97280
grep HugePages_ /proc/meminfo
```

Or at boot in the kernel command line: `hugepagesz=1G hugepages=190`. This host has 246.8 GiB; after 190 GiB of hugepages about 56 GiB remains for the OS and the serving process, which is enough for SGLang's host-side buffers but not for a second large model. Revert with `vm.nr_hugepages=0`.

If the GLM container is running, `docker stop glm53-flash-2x-rtxpro6000` first; it pins host memory.

## SM120 pitfalls reported by the community for DeepSeek-V4 / V4.1

From vLLM issues #47266 and #56700 and the 0xSero SGLang recipe. Not all reproduce on every build; check before applying.

| Symptom | Cause | Mitigation |
|---|---|---|
| Server hangs at startup with no log progress | DeepGEMM / FlashInfer autotune on SM120 | Disable autotune for the affected backend; SGLang cookbook says leave backends on auto |
| Crash during CUDA graph capture | Capture pool exceeds memory or unsupported kernel in graph | `--enforce-eager` (vLLM) / `--disable-cuda-graph` (SGLang); expect lower decode throughput |
| Wrong answers only on prompts ≥ 100K tokens | FP8 KV scale layout bug | Use `KV_CACHE_DTYPE=auto` (BF16) or a build that includes the fix; `verify.py --context 262144` catches it |
| MXFP4 experts run slowly | Marlin fallback instead of native FP4 grouped GEMM (vLLM #30135) | Check the kernel selection in the server log; compare against SGLang's FlashInfer MXFP4 path |
| All-reduce errors or NCCL hang on PCIe boxes | Custom all-reduce on non-NVLink topology | `--disable-custom-all-reduce` (vLLM); confirm `nvidia-smi topo -p2p r` shows OK |
| Sparse MLA dispatch error | FlashInfer SM120 dispatch gap for some head configurations | Use the SGLang preview image, which the 4-GPU recipe proved on SM120 |

## `dsv41-kt` dies at decode graph capture with `ImportError: libnvrtc.so.12`

Seen on the first T3.6d serve (2026-09-21). The traceback ends in `deep_gemm/__init__.py`, reached from `deepseek_v4_backend._fp4_paged_mqa_logits`. The base image (`dev-dsv41`, CUDA 13) is fine; the culprit is `pip install --no-deps kt-kernel==0.7.0.post4`. That wheel vendors ~1,000 files that are not kt-kernel at top level — a cu12 `deep_gemm` (832 files, 139-line `__init__` without `fp8_fp4_paged_mqa_logits`), `sgl_kernel` **0.3.21** (replacing 0.4.6.post1 and its `flashmla_ops`/`spatial_ops` `.so`), `triton_kernels`, `flash_attn_origin`, mscclpp — and `--no-deps` unpacks all of them over the base copies. `kt_kernel` itself imports none of them.

Fix (in `config/Dockerfile.dsv41-kt` since this date): download the wheel, run `config/prune_wheel.py` to keep only `kt_kernel/`, `kt_kernel.libs/` and the dist-info, install the pruned wheel. `config/kt_smoke.py` now fails the build if `sgl_kernel/version.py` ≠ 0.4.6.post1, if `deep_gemm/__init__.py` lacks the function, or if any `deep_gemm/*.so` links `libcudart.so.12`/`libnvrtc.so.12`. Rule for any future `--no-deps` install: list `site-packages` top-level entries before and after and diff them.

Do not "fix" this by installing `sgl-deep-gemm==0.2.0` or by moving the image to CUDA 12 — the base already has the right cu13 deep_gemm; the job is to stop overwriting it.

Runs made on the clobbered image (E17 one-layer test, E18 Engram bench) did not touch `sgl_kernel` or `deep_gemm`, so their numbers stand.

## `dsv41-kt` dies in `deep_gemm.fp8_fp4_paged_mqa_logits` with `deep_gemm_metadata=None`

Second T3.6d blocker (2026-09-21). On SM120 SGLang defaults `SGLANG_FP8_PAGED_MQA_LOGITS_TORCH=1` and `SGLANG_OPT_USE_TILELANG_INDEXER=1` (the torch/TileLang fallbacks for the indexer), but V4.1-Flash's low-ratio indexer calls the FP4 DeepGEMM kernel unconditionally and expects the metadata those fallbacks never build.

Fix: launch with `--enable-deepseek-v4-fp4-indexer` **and** `-e SGLANG_OPT_USE_TILELANG_INDEXER=0 -e SGLANG_FP8_PAGED_MQA_LOGITS_TORCH=0`. The cu13 `deep_gemm` in `dsv41-kt:recipe` runs the FP4 indexer on SM120 fine once it is actually asked to.

## `Unsupported BCG output type: LogitsProcessorOutput` from the breakable decode graph

Third T3.6d blocker. `--cuda-graph-backend-decode breakable` (needed because the Engram `file` lookup is a graph break) copies outputs between graph segments and only knew tensors and containers, not the `LogitsProcessorOutput` dataclass the model returns.

Fix: overlay commit `cd55166a` (`breakable_cuda_graph_backend.py`) recurses into dataclasses. Upstream instead moved logits out of the graph (#40222) and no longer needs `breakable` for Engram; our `file` layout still does, so keep the overlay until the layout is ported onto that design.

## `sparse_mla_sm120_prefill.cu dispatch_dsv4_dual` aborts during the server's warmup prefill

Fourth T3.6d blocker. FlashInfer 0.6.18 compiles the SM120 DSv4 dual-pool prefill kernel only for `extra_page_block_size ∈ {64, 2}`. SGLang pages each compressed KV pool at `page_size // compress_ratio`, so with the default 256-token page the V4.1 pools come out at c1 = 256, c2 = 128, c4 = 64, c128 = 2 — and V4.1's `compress_ratios` (5×0, 20×1, 18×2) means 20 layers hit the unsupported 256 and 18 more the unsupported 128. The decode kernel takes `pbs_extra` at runtime and is unaffected; only prefills with more than 64 query rows (the warmup, every real prompt) crash.

Fix: overlay `cd55166a` in `flash_mla_sm120.py` — when the extra pool's page size is not 64 or 2 and divides by 64, re-page the touched pages to 64 through `_split_kv_pages_to_64(..., buffer_tag="extra")` (the tag keeps a separate cache buffer from the SWA split). Cost: ≈ 2–3 GB per card out of the ≈ 7 GB "available" pool; GPU used went 90 → 93.1 GB per card. A real fix is a FlashInfer build that instantiates 128/256, or running SGLang with `--page-size 64`.

## DSpark on: `illegal memory access` in `dspark_verify.py … breakable_cuda_graph.py replay → seg.replay()` on the first decode after a long prompt

E23 attempts 5–7. Short prompts (≤ 512 tokens) speculate, but with a low accept rate (0.26–0.57) and garbled tool calls; the first target-verify step after a 5,376- or 13,463-token prompt dies with `cudaErrorIllegalAddress` inside the breakable graph replay. `CUDA_LAUNCH_BLOCKING=1` names no kernel because the fault surfaces at graph replay. **Eager mode runs the same prompt correctly** (needles 3/3, accept rate 0.77, tool call parsed), so the graph replay, not the kernels, is wrong.

**Status: fixed 2026-09-23 (overlay `838490a6`) — two independent bugs, both in the CUDA-graph path.** A third, only at four concurrent requests, is the next entry (bug C, kt-kernel). All three share one shape — a captured graph holding a pointer that the eager path later frees — and one diagnostic: log allocations with a `capturing` flag and compare the sizes the graph asked for with the sizes the cache registered.

- **Bug A — wrong tokens / low acceptance in graph mode (accept 0.26–0.57, garbled tool calls; eager 0.77).** Root cause: the model's multi-stream overlap (`alt_streams`) runs inside the captured verify graph and the side-stream work is not ordered against the main stream at replay. `SGLANG_OPT_USE_MULTI_STREAM_OVERLAP=0` restores eager-equivalent output (probe 171 tokens exact, 3-needle verify 7/7, accept ≈ 0.9 on the counting probe, 0.6–0.7 on prose). The recipe passes it through `EXTRA_DOCKER_ENV` for every DSpark launch; the proper fix (gate the overlap off only for spec draft/verify forwards) is T3.9 follow-up work.
- **Bug B — `cudaErrorIllegalAddress` / Xid 31 in the first attention layer of a verify step, second request or first mixed batch.** Root cause: `_split_kv_pages_to_64` in the overlay's `flash_mla_sm120.py` kept its page mask and split-output buffers as *grow-only* tensors in `get_resources().buffers` and **freed the old tensor on growth**. Warmup only touches the SWA pool (mask N=71), the verify graphs were captured with that pointer baked into the `zero_()` memset and the `_page_mark_kernel`/`_page_split_kernel` launches, and the first real prefill after capture grew the shared mask to N=1093–1206 for the compressed pools. Every replay then wrote the freed block: while the caching allocator reused it the graph-input dump showed `positions`/`out_cache_loc` reading back as int8 page marks (`65792` = bytes `00 01 01 00` = pages 1,2 marked), and once the segment was released the captured write hit unmapped memory. Eager never faults because it always uses the current buffer. Fix: retired buffers stay alive for the process (a graph is self-consistent with the buffer it captured because a pool's page count is static), `reserve_split_buffers()` pre-sizes mask and split buffers from the real pool geometry at backend init (log line `[sm120-split] reserved page-split buffers from pools …`), a grow after capture logs at ERROR, and `_page_mark_kernel` drops indices ≥ pool size. Discriminator ladder that got there: layer-granular graph breaks (`SGLANG_BCG_DEBUG_LAYER_BREAKS=all`) put the fault in layer 0 → in-graph index guard (`SGLANG_SM120_IDX_GUARD=1`) counted zero out-of-range indices → graph-input dump (`SGLANG_BCG_DEBUG_INPUTS=1`) showed the page-mark bytes → allocation log with pointers showed the grow after capture. Fixed run: probe/verify pass, C1/C3/C4 512-token matrix completes with zero faults.
- Not the cause (ruled out on the way): attention indices past the pool (guard counted 0), stale `full_to_swa_index_mapping`, kt-kernel buffer overwrite, sampler, MTP heads, Engram. FlashInfer's SM120 sparse-MLA kernel treats negative indices as invalid but has **no upper-bound check** on positive ones, which is why a bad index would have been silent.

Earlier hypothesis tested and falsified (attempt 8): `DeepseekV4AttnBackend.shared_read_ends` returns `IN_REPLAY` for DSpark target-verify on the assumption that "DSPARK verify replays one full (non-breakable) graph", while our recipe runs `--cuda-graph-backend-decode breakable` (the Engram `file` lookup is a graph break), so later segments re-read scheduler-shared buffers (`req_to_token`, KV metadata) after the in-graph marker and the overlap scheduler could rewrite them for the next batch mid-verify. The non-DSpark branch of the same function says `POST_REPLAY` for that reason, so the overlay was changed to return `IN_REPLAY` only when `check_cuda_graph_backend(Phase.DECODE, Backend.BREAKABLE)` is false. **The IMA reproduced unchanged with that fix in place** (attempt 8 log, local `evidence/e23-spec-decode/crash/attempt8-shared-read-fix-still-ima.log`; `*.log` is gitignored), so the early marker is at most a latent race, not this fault. The change is kept because the non-breakable assumption is still wrong for this recipe, but it is not the fix.

Bisect steps that were planned before the fix (kept for the method; `--debug-cuda-graph` was not needed in the end): `EXTRA_SERVER_ARGS="--debug-cuda-graph"` (every op eager, but through the same segmented capture/replay path — separates "kernel inside a replayed segment" from "segment plumbing"); then the target-verify metadata path — the decode runner's `init_forward_metadata_out_graph` / `init_forward_metadata_in_graph` and the verify branch of `deepseek_v4_backend.py` — checking that the per-segment metadata (`seq_lens`, KV indices, the re-paged extra pool from the `_split_kv_pages_to_64` fix) is sized for `bs × (K+1)` tokens after a long prefix, since short prompts survive and long ones fault.

Two traps met on the way:
- `--disable-cuda-graph` is `no_cli` in this fork and, in `arg_groups/cuda_graph_hook.py`, the explicit `--cuda-graph-backend-decode breakable` that `serve-hybrid.sh` always passes wins over both `--disable-cuda-graph` and `--disable-decode-cuda-graph`. To run eager, append `EXTRA_SERVER_ARGS="--cuda-graph-backend-decode disabled"` (argparse last-wins). `--debug-cuda-graph` is the middle ground: every op eager but still through the breakable capture/replay path.
- Eager target-verify on the vision-capable DSV4 model entered `_prepare_mm_embeddings` (TARGET_VERIFY is `is_extend()` and text-only requests still carry a `MultimodalInputs` object) and died with `TypeError: 'NoneType' object is not iterable` in `_count_mm_tokens_in_extend` because a verify batch has no `extend_prefix_lens_cpu`. Overlay fix in `models/deepseek_v4.py`: skip the mm-embedding branch for `is_decode_or_idle()` and `is_target_verify()`, matching the vision check two lines below. Graph mode never saw it because the captured dummy batch has `mm_inputs=None`.

## DSpark on, four concurrent requests: rank 0 dies with `Fatal Python error: Segmentation fault` in `torch/cuda/graphs.py replay` — or Xid 31 `ENGINE CE4 … FAULT_PDE ACCESS_TYPE_VIRT_WRITE @ 0x0`

E23 R1 (K=5, D=4) and R2 (K=5, D=0). C1, C2 and C3 pass; **every C4 run** dies in the target-verify replay, either as a host segfault inside `cuGraphLaunch` (rank 0 only, all worker threads idle, the scheduler thread in `dspark_verify.py run_non_compact → _forward_prepared_verify → decode_cuda_graph_runner.execute → BreakableCUDAGraph.replay → seg.replay()`), or as a copy-engine MMU write fault surfacing later as `CUDA error: unspecified launch failure` in the Engram graph break. `KT_MAX_DEFERRED=0` did not change it (R2), so it is not the deferral path. `SGLANG_BCG_DEBUG_SYNC=1` with the new pre-segment-0 sync passed silently, so the fault is in the graph launch itself, not inherited from the preceding prefill or draft step.

**Status: root-caused and fixed 2026-09-23 (Bug C; kt-kernel, not the overlay).** Patch `config/kt-kernel-patches/0001-experts-base-temp-buffer-lifetime.patch`, applied by `config/Dockerfile.dsv41-kt`; until the image is rebuilt, bind-mount it with `EXTRA_DOCKER_ARGS` (see `scripts/serve-hybrid.sh`). Evidence `evidence/e23-spec-decode/r3/`.

- **Root cause — a CUDA graph baked kt-kernel's single reusable *temp* pinned buffer, which the next eager call freed.** `kt_kernel/experts_base.py KExpertsCPUBuffer.get_buffer(hidden_states)` keys its pinned host buffers (input, expert ids, weights, output, bsz) and the `output_gpu` tensor on the flattened token count. Sizes listed in `capture_bs` get a permanent entry in `capture_buffers`; any other size shares **one** class-level `temp_buffer`, replaced (and thereby freed) whenever a different size arrives. The check order is `capture_buffers` → `temp_bs` → allocate, so a size that was first requested *before* SGLang called `KTMoEWrapper.set_capture_batch_sizes(...)` is stuck in the temp slot even after it is registered. That is exactly what happens under speculation: the flashinfer AutoTuner dummy forward runs the max verify shape (bs 4 × 6 tokens = **24**) 26 s before the target-verify runner exists, while `capture_bs` is still `[]` (`KT_BUF alloc temp buffer bs=24 (prev temp_bs=0, capture_bs=[], captured=[])`), then the bs=4 verify graph is captured and `get_buffer(24)` returns the temp tuple — the graph bakes its D2H/H2D memcpy nodes and the host-callback task pointers to it — then the bs=3 capture allocates 18 and **replaces the temp**. The final cache reads `captured=[6, 12, 18]`: 24 is missing. Every later bs=4 verify (only C4 reaches it) copies into freed pinned memory: a host segfault when the driver touches the unmapped host pages at launch, or a CE write fault if the copy runs. ~~Spec-off C4 has been stable since E21, consistent with the plain decode runner registering `[1, 2, 3, 4]` before its autotune dummy run (inferred from the code order, not re-verified with the instrumentation).~~ **Corrected 2026-09-23 (same day, after the image rebuild):** the plain spec-off decode graph has the *same* defect at bs=4 — the rebuilt image logs `KT_BUF promote temp buffer bs=4 into capture_buffers (capture_bs=[1, 2, 4])` during capture, so on the unpatched build the bs=4 decode graph was baked to the temp tuple that the first prefill freed. It never crashed because the freed pinned pages stayed mapped in torch's caching host allocator and were recycled by later tuples; it **silently corrupted rows 1–3** instead — see the next entry.
- **Fix 1 (root cause):** when `get_buffer` finds the size in the temp slot *and* in `capture_bs`, promote the exact tuple into `capture_buffers` instead of returning the temp (log line `KT_BUF promote temp buffer bs=24 into capture_buffers`); the final cache is now `[6, 12, 18, 24]`.
- **Fix 2 (defence in depth):** replaced temp buffers are retired behind a `torch.cuda.Event` recorded on the current stream and only dropped once `event.query()` is true (bounded list, oldest synchronised if > 16 pending). kt's eager path is fully stream-asynchronous — `copy_(non_blocking)` D2H → `submit_with_cuda_stream` host callback → CPU experts → H2D — and the C++ tasks hold raw `data_ptr()`s that torch's caching host allocator cannot see, so back-to-back different-size prefills (the R3 log shows 193 → 166 → 132 → 256-token temps seconds apart) could free a buffer the CPU workers were still writing. No crash was attributed to this path, but it is the same class of bug.
- **Verification:** no fix → C4 segfault on the first verify (`r3/k5-d0-nofix-c4-segfault.txt`); with the patch → C4 96/128/128-token probes 3/3 pass at K=5 D=0, then the full K=5 D=4 matrix (`r3/k5-d4-fix.*`), zero Xid in the kernel log. Diagnostic that found it in one launch: log every `get_buffer` allocation with `capture_bs`, the registered keys and `torch.cuda.is_current_stream_capturing()`; the culprit is the size that appears in a capture but never in the registered list.
- **Upstream status:** kt-kernel `main` still has the single temp slot (checked 2026-09-23); issue kvcache-ai/ktransformers#1815 (two RTX PRO 6000, four running requests, SIGSEGV with speculative decoding — "we do not support speculative decoding currently") and #2009 (MTP SIGSEGV in graph replay) are this bug. Candidate PR in `docs/research/OPEN-SOURCE-PLAN.md`.
- Ruled out on the way: deferral (R2), token-count vs C++ scratch limits (`_check_qlen_fits_cpp_buffers` uses `chunked_prefill_size`), overlap-scheduler ordering (pre-segment sync), the SM120 page-split scratch (Bug B, already fixed), a DSpark buffer sized `max_bs` indexed by pool slot (all `max_bs` buffers are indexed by batch position).

## C4 decode drops from ≈ 148 to ≈ 50 tok/s after the bug C patch — and four identical greedy prompts in one batch return four different answers on the old build

**Status: understood 2026-09-23. The patched speed is the correct one; the old C3/C4 speed was the bug.** Evidence `evidence/e23-spec-decode/r3/batch-consistency/` and `r3/decode-patched-*.json`; the doc-wide correction is the "Erratum" section in [BENCHMARKS.md](BENCHMARKS.md).

- **Symptom that started it:** the rebuilt image (`dsv41-kt:recipe`, bug C patch applied) ran C1 at 38.4–39.2 tok/s as before but C4 at 49–51 summed / 45–47 wall instead of the 145–148 / 132 recorded since E19. A/B with the pristine `experts_base.py` bind-mounted over the patched image (`EXTRA_DOCKER_ARGS="-v <pristine>:/opt/sglang/lib/python3.12/site-packages/kt_kernel/experts_base.py:ro"`) restored C4 148 — so the patch, not the rebuild, changed the number. A variant that allocates a fresh permanent tuple at capture instead of promoting the temp was equally slow, so buffer *identity* was not the mechanism. `py-spy` on the TP0 scheduler during C4 decode: 90 % of samples blocked in the Engram eager break's D2H copy (`engram.py _engram_file_rows`), i.e. waiting for the captured segment; zero samples in kt Python — the extra ≈ 53 ms per bs=4 step was inside the graph segment (CPU-expert host callbacks), not Python overhead.
- **Why the old build was fast:** the unpatched bs=4 decode graph's memcpy nodes and host-callback task pointers referenced the freed temp tuple. The C++ task reads the batch size and the expert ids through those raw pointers; after the first prefill recycled the pages, the bs=4 graph computed CPU experts for effectively one row and copied stale bytes for the rest — so its step time equalled a bs=1 step, which is exactly the "near-linear batching" the recipe reported. Same-prompt vs distinct-prompt C4 "costing the same" (E19 item 3) was the same bug.
- **Correctness test (new gate, `scripts/verify-batch-consistency.py --same-prompt`):** four identical greedy prompts submitted together (temperature 0, one bs=4 batch); rows must come back byte-identical, or at least share hundreds of characters (rows admitted at different steps see a different batch composition for their first tokens — legitimate drift, typically ≥ 200 chars). Pristine build, C4: row 0 matches the bs=1 reference for 502/509 chars, rows 1–2 diverge at char 16 with a different (still fluent) essay, row 3 answers `The phrase "Explain" is incomplete and lacks context` — it lost the prompt (`batch-consistency/pristine-same-c4.json`). Pristine C3: rows 1–2 diverge at char 16 (bs=3 pads into the bs=4 graph). Pristine C2: both rows correct (bs=2 had a permanent buffer). Patched image: C3 rows byte-identical, C4 min pairwise prefix 225 chars (`patched-same-c3.json`, `patched-same-c4.json`). The E19 "greedy 12-token logprob check at bs=4" that passed compared only the first stream — row 0, the one row the bug computed correctly.
- **What the correct speed says about the CPU tier:** patched image, D=4, 256 tokens, distinct prompts, 3 runs: C1 39.2 summed / 34.0 wall, C2 44.9 / 40.6, C3 38.3 / 35.8, C4 50.8 / 47.0 (`r3/decode-patched-c1234.json`). Step time ≈ 8 ms + 17.7 ms × rows. Same-prompt C4 (all rows route to the same experts) is 56.2 / 49.6 — only 11 % faster than distinct — so kt's CPU cost is per (token, expert) evaluation, not per distinct expert's weight bytes: at M ≤ 4 the MXFP4 CPU kernel does not amortise weight reads across rows. Batching is worth ≈ +30 % aggregate at C4 for a 3× lower per-stream rate; C3 loses to C2 because it pads to the bs=4 graph.
- **Rules that come out of it:** (1) every captured batch size gets the same-prompt gate before a number is recorded (TASKS standing rules); (2) any scaling result that is *better* than the cost model predicts is a bug signal first, a discovery second; (3) quality gates (`nll-score.py`, `verify.py`) run at bs=1 and cannot see a row-2..N defect — do not read a passing NLL as evidence about concurrency.

Device-side assert in sampling on the first decode after a 4-sequence prefill with **distinct** prompts; the async error surfaces wherever the next sync happens (`engram.py _engram_file_rows` inside the breakable replay), which is misleading. ## `dsv41-kt` dies at decode graph capture with `operation not permitted when stream is capturing` from `kt_ep_wrapper.py … _nan_probe`

You launched with `KT_NAN_PROBE_MIN_TOKENS` set low enough (e.g. `1`) that the E22d NaN probe runs on decode-sized forwards. The probe does a host sync (`(~torch.isfinite(t)).sum().item()`), which CUDA forbids inside a graph capture; the capture is invalidated, the runner raises `Capture cuda graph failed: … cudaErrorStreamCaptureInvalidated`, and the scheduler exits. Seen 2026-09-23 on the first E27 soak launch (`KT_NAN_PROBE_MIN_TOKENS=1`, capture list `1 2 3 4`). Fixed in overlay `cad73914`: the probe is skipped while `torch.cuda.is_current_stream_capturing()`. Consequence worth knowing: the probe can only see prefill and eager decode steps — a decode step replayed from a captured graph is never probed, whatever the threshold. A graph-compatible probe (device-side flag buffer checked after replay) is a T3.16 item, not yet built. The same rule applies to any new debug hook in the kt path: nothing that syncs the host may run under capture (T3.16a).

## C3 decode is slower than C2 (three concurrent streams get ≈ 38 summed tok/s, two get ≈ 45)

**Cause.** `--cuda-graph-max-bs-decode 4` makes SGLang derive the capture list `[1, 2, 4]`; a 3-row decode batch is padded into the bs=4 graph and the CPU tier streams four rows' worth of expert weights for three tokens (E26 B1: 38.3 vs 49.0 summed tok/s once bs=3 is captured).

**Fix.** Capture every batch size you serve: `serve-hybrid.sh` now passes `--cuda-graph-bs-decode 1 2 3 4` (`CUDA_GRAPH_BS`, default `"1 2 3 4"`; `--cuda-graph-bs` is a deprecated alias in this fork). Confirm in the launch log: `Capture target decode CUDA graph begin. backend=breakable, … bs=[1, 2, 3, 4]` and `KT_BUF promote temp buffer bs=4 into capture_buffers (capture_bs=[1, 2, 3, 4])`. Run `verify-batch-consistency.py --same-prompt` at C2/C3/C4 after any change to the list (bug C lived in exactly this buffer).

## `kt-cpu-per-step.sh` says all 16 kt threads are busy at every concurrency

Not a measurement of work. kt-kernel workers busy-spin for 50 ms before sleeping on their condition variable, and no per-layer CPU wait is that long, so every worker burns CPU for the whole step whether it computes or waits; CPU-seconds per step ≡ 16 × step wall (E26 B4: 15.6–15.8 "busy" at C1 through C4). To see whether the tier is compute- or bandwidth-bound, sample the memory controller instead — `python3 scripts/hsmp-clocks.py --watch 1 --n 45 --json out.json` beside a decode run (unprivileged; socket-wide traffic at 1 s resolution). E26 B4′: ≈ 98 GB/s of the 125 GB/s two-CCD ceiling at bs=1 → bandwidth-bound.

## Decode collapses to ≈ 5 tok/s (or loses 10–15 %) after raising `KT_CPUINFER`

Seen 2026-09-23 (E26 A1) on the 16-core / 32-thread 9955WX: `KT_CPUINFER=24` gave C1 29.9 wall tok/s (−12 % vs 16), `KT_CPUINFER=30` gave **4.9** (−86 %) and 4K prefill fell 862 → 471 tok/s; nothing crashed, `nvidia-smi` showed the GPUs mostly idle. kt-kernel pins one worker per hwloc *core* and each worker busy-spins for 50 ms after every job before sleeping (`cpu_backend/worker_pool.cpp`); workers beyond the core count fail affinity and float on SMT siblings, where they starve the two TP-rank launch threads. Fix: `KT_CPUINFER` ≤ physical cores (16 here; 14 is equal within noise). `serve-hybrid.sh` prints a warning when the value exceeds `lscpu`'s core count. Do not "fix" this by disabling SMT in the BIOS — the recipe's Python, NCCL and Engram threads live on the siblings (BIOS guide §3, SMT row).

## Boot floods the console/journal with `Hardware Error … Global Memory Interconnect PCS Unit … Corrected error` after a BIOS clock change

**Symptom.** POST passes, DRAM trains, then from ≈ 1–3 s into the kernel the console scrolls thousands of `mce: [Hardware Error]: … Bank 16 … Global Memory Interconnect PCS Unit Ext. Error Code: 6 … Corrected error, no action required.` lines (≈ 500/s, `mce_gen_pool_process hogged` warnings). No DRAM EDAC counts. Seen 2026-09-23 after setting Infinity Fabric Frequency and Dividers = 2100 MHz with all voltages Auto (E27 T3-F1).

**Cause.** The GMI (CCD↔IO-die) link is not clean at the requested FCLK. "Corrected" means the link is retrying every transaction, not that it is fine — the machine is not usable and the fabric has no ECC of its own to lean on.

**Fix.** Do not add voltage. Forensics on the failed boots without needing a shell during them: `journalctl --list-boots`, then `journalctl -k -b -1 --no-pager | grep -c 'Hardware Error'` and `… | grep -E 'Bank|Ext. Error Code|IPID|Syndrome' | sort | uniq -c`. Redact PPIN and hostname before committing. Record the trial as failed in BIOS guide §7 — the protocol stops the tier on any MCE (`evidence/bios-trials/2026-09-23-boot4-t3f1-fclk2100/`).

## `Using default W8A8 Block FP8 kernel config. Performance might be sub-optimal!` (and the server is slow, not broken)

Not a crash — one WARNING line per dense shape at startup, easy to miss, and worth ~2× of the decode step (E20). Without one, the default config runs the seven V4.1-Flash dense shapes at 60–80 GB/s on a 1,600 GB/s card: 40 ms of a 70 ms bs=1 step (T3.6d3 profile).

Fix: `kernels/e20/tune_w8a8_block32.py` (run inside the container, see its docstring) writes the seven JSONs; copy them into the overlay's `python/sglang/kernels/ops/quantization/configs/` (bind-mounted, so no image rebuild) and make sure the overlay carries the `is_sm120` gate lift in `fp8_kernel.py::w8a8_block_fp8_matmul_triton` — the tuned configs use `SPLIT_K`/`SWAP_AB`, which stock SGLang only honours on SM90. Check the fix took: the warning disappears and `Using configuration from … for W8A8 Block FP8 kernel.` appears for each shape. ## Thinking mode surprises

DeepSeek-V4.1 reasoning is on by default at effort 50 in both engines. Every client in this repo sends `chat_template_kwargs: {"thinking": false}` unless asked otherwise. If your own client sees long, slow answers, that is why. The recipe's smoke test is `17*19` → `323`.

## Weight load is slow

475 GiB from NVMe at ~14 GB/s is at least 33 s of pure I/O; the engine's dequant and layout passes dominate, and the Engram host-table copy adds a pass over 189 GiB. Ten to thirty minutes is normal on the 4-GPU profile. `wait-ready.py` defaults to a one-hour timeout.

## `download-model.sh` refuses to start

It needs ~500 GiB free at `MODEL_DIR`. On this host nvme0 has 1.7 TB free; make sure `MODEL_DIR` is on it and not on a smaller volume. The checkpoint interleaves vision, DSpark and text tensors across all 48 shards, so a partial download cannot save space.

## `ci.sh` reports "possible identifier or secret"
