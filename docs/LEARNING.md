# Learning guide

A reading map for every piece of this project, written for the owner. Each section says why the piece matters *for this build*, what to read (primary sources first), and where it shows up in this repo so you can connect the reading to a file you can run. Read in order the first time; afterwards jump to whichever experiment you are about to run and read its row in the last table.

Difficulty marks: ★ background, ★★ working knowledge needed to run and interpret experiments, ★★★ needed to write or modify kernels.

## 0. The one-paragraph map

We want a 475 GiB model on 192 GiB of VRAM. The model is a Mixture-of-Experts (MoE): most of its weights are "experts" of which only 6 of 384 fire per token, so weights that are not in VRAM only cost bandwidth when they are used. That turns the problem into memory-hierarchy engineering — VRAM (1.79 TB/s) → host DRAM (~150–300 GB/s) → NVMe (~14 GB/s, but 400K random rows/s) — and into kernel engineering, because the tensor cores on our RTX PRO 6000 (SM120) run 4-bit math natively only through a specific instruction that no serving engine uses yet on this card. Everything in `plan/` is one of those two threads.

### 5.1 Why a correct GEMM can run 20× below the roofline: tiles, occupancy, split-K (E20)

E19's profile put 57 % of the V4.1 decode step in one Triton kernel, `_w8a8_block_fp8_matmul`, doing the *dense* FP8 GEMMs (attention projections, shared expert, dense MLPs). Nothing was wrong with it: same math, right answer, tuned on H100/H200. It was 20× slower than the memory system allows. Understanding why is the most transferable lesson in the kernel track, because it is the failure mode of every "it works on H100" kernel on a new GPU.

**The mental model.** A decode GEMM has M = batch (1–4 tokens), N = output width (1.8K–25.6K), K = input width (1.1K–6K). The weight matrix is N×K bytes of FP8 and must be read once per step; the activations are tiny. So it is a *memory-bound* op and the only question is how many bytes per second the kernel pulls from GDDR7. Roofline: 21 MB (5120×4096) at 1.6 TB/s ≈ 13 µs.

**How a tiled GEMM turns that into work.** Triton (and CUTLASS) launch one CTA per (BLOCK_M × BLOCK_N) output tile; each CTA loops over K in BLOCK_K slices, loading an A tile and a B tile per iteration and feeding `tl.dot`. Three knobs decide whether the memory system is kept busy:

1. **Grid size (parallelism).** CTAs in flight = (M/BLOCK_M) × (N/BLOCK_N). With M=1 that is just N/BLOCK_N. The default here was BLOCK_N=32 → 160 CTAs for N=5120 on a 188-SM card: under one CTA per SM, and each CTA is 4 warps. The profile read this as 2–3 % occupancy.
2. **Bytes in flight per CTA (pipelining).** Each iteration loads a BLOCK_K × BLOCK_N slice of B — 32×32 = 1 KB here. `num_stages` is how many iterations are prefetched ahead (software pipelining through shared memory). 160 CTAs × 3 stages × 1 KB ≈ 0.5 MB outstanding. GDDR7 needs several MB outstanding to hide its latency (Little's law: bandwidth × latency ≈ 1.6 TB/s × ~600 ns ≈ 1 MB minimum, more in practice). The result is a latency-bound serial walk down K.
3. **The K loop length.** K/BLOCK_K iterations, each a dependent step. With BLOCK_K pinned at 32 by the scale layout (below), K=4096 is 128 serial iterations per CTA.

**Why BLOCK_K is stuck at 32.** V4.1-Flash quantises dense weights with a per-(32×32)-block FP8 scale (`block_shape=[32, 32]` in the checkpoint's `quantization_config`). The kernel applies the scale once per K-tile (`n_tiles_k_per_group_k = group_k // BLOCK_SIZE_K`), so BLOCK_K must divide 32. DeepSeek-V3 used 128×128 blocks, and every tuned config SGLang ships is for 128 — which is also why its tuner filters `block_k % BLOCK_SIZE_K == 0` over a `{64, 128}` search space and finds nothing for 32. BLOCK_N is *not* constrained: the kernel indexes the scale per column (`offs_bn // group_n`), so a 64- or 128-wide N tile just reads two or four scale columns.

**The two fixes, and why they are the same fix.** Both raise bytes-in-flight:

- **Split-K.** Launch SPLIT_K CTAs per output tile, each doing K/SPLIT_K of the loop into an FP32 partial buffer, then a reduce kernel sums the partials. Grid ×8 at the cost of an 8×M×N×4-byte scratch buffer (trivial at decode M) and one extra small launch. This is what the existing `_w8a8_block_fp8_matmul_hopper` kernel does; SGLang gated it to `is_sm90` only because that is where it was tuned — the kernel is portable Triton with no Hopper intrinsics.
- **SWAP_AB.** For M < 16 the MMA instruction's minimum M tile (16) wastes 15/16 of the A rows. Transposing the problem (compute Cᵀ = Bᵀ Aᵀ) puts the weight's N dimension on the MMA's M axis, so the wide operand fills the instruction and the tiny batch sits on N. Same bytes, fewer wasted MMA lanes, and a larger effective tile per CTA.
- More `num_stages` (4–5) and fewer warps (2) also help at these sizes: fewer warps per CTA means more CTAs per SM's register/smem budget; more stages means more outstanding loads per CTA.

**How the engine picks a config.** `get_w8a8_block_fp8_configs(N, K, block_n, block_k)` looks for `configs/N=…,K=…,device_name=<nvidia-smi name with underscores>,dtype=fp8_w8a8,block_shape=[bn, bk].json`; the JSON maps batch sizes to configs and the runtime picks the key nearest to M. No file → the default `{BLOCK_M 64, BLOCK_N block_n, BLOCK_K block_k, 3 stages}` and a one-line warning at rank 0 that is easy to miss in 600 lines of startup log. Two consequences worth remembering: (a) the device name is part of the key, so a config tuned on "RTX PRO 6000 Blackwell Max-Q Workstation Edition" is not found by the non-Max-Q card; (b) the nearest-M lookup means a config file tuned only at small M would hand prefill (M=4096) a decode config — tune both ends.

**How E20 tuned it** (`kernels/e20/tune_w8a8_block32.py`): import SGLang's own kernels, build the search space the stock tuner cannot (BLOCK_M 16, BLOCK_N 16–128, SPLIT_K 1–16, SWAP_AB, 2–8 warps, 2–5 stages for M ≤ 16; conventional tiles for M ≥ 32), time each with `triton.testing.do_bench` (CUDA events, L2 flushed), then check the *winner* against an FP32 dequantised reference before writing it — a fast kernel that silently disagrees is worse than a slow one. Verdict and numbers: E20 in EXPERIMENTS.md.

### 6.1 Eager vs CUDA graphs — why it matters on this box, and why eager is not a fallback

**What "eager" means.** PyTorch's default execution is eager: Python calls an op, the op picks a kernel, the CPU asks the driver to launch it, then Python moves to the next line. Every kernel is a separate round trip through Python → PyTorch dispatcher → CUDA runtime → driver. A single V4-Flash decode step runs several hundred of those (E12 counted 236 launches of one block-scaled GEMM alone, plus attention, norms, routing, gathers, sampling), and DSpark verifies 6 tokens per step so the graph is longer still.

**Why that is slow.** A kernel launch costs the CPU roughly 5–10 µs of driver work plus whatever Python spent deciding to launch it (shape checks, dtype dispatch, allocator calls). The kernels themselves, at batch 1, are tiny — a few microseconds each, because decode is memory-bound and reads weights once per step. So the GPU finishes each kernel before the CPU has finished issuing the next one. The GPU then sits idle waiting for orders. E15 measured exactly this: eager V4-Flash without speculation took **63 ms per step vs 11.2 ms with graphs**, and the cards drew only 142–155 W at full clocks — powered up, waiting. That is 15.9 tok/s instead of 89, a 5.6× loss, with the same kernels and the same weights.

**What a CUDA graph is.** You run the step once in "capture" mode; instead of executing, the driver records every kernel, its arguments and its dependencies into a graph object. Afterwards `cudaGraphLaunch` replays the whole step as one submission: one CPU call, hundreds of kernels, no Python in the loop. The GPU runs them back to back from its own queue. The step becomes GPU-bound again, which is what a memory-bound decode should be.

**Why there is a "capture size."** A graph bakes in tensor shapes. A decode step for 1 sequence and for 16 sequences are different graphs, so the engine captures one per batch size up to `max_cudagraph_capture_size` (vLLM captures 1, 2, 4, 8, 16, 24, … up to the ceiling; GLM's log listed 27 sizes up to 192). If a batch arrives with more tokens than the largest captured graph, that step runs eager. With speculation each sequence contributes K+1 tokens per step (5 draft + 1 target), so the ceiling must be `MAX_NUM_SEQS × (K+1)`: 16 × 6 = 96. This is why the V4-Flash sibling's old `MAX_CUDAGRAPH_CAPTURE_SIZE=16` was a hidden trap — with 2 slots it covered 12 tokens and was fine; at 16 slots anything beyond ~2 active sequences would have dropped into the 5× slower path. Capture costs some VRAM (a graph pool: 0.30 GiB for GLM's 27 graphs, ~0.5 GiB for V4-Flash's) and startup time (73 s for GLM). Both are one-off.

**FULL_DECODE_ONLY, PIECEWISE, and torch.compile.** vLLM can capture the whole decode step as one graph (`FULL_DECODE_ONLY`, what V4-Flash uses) or capture pieces between operations it cannot graph (`PIECEWISE`, what GLM's runtime profiles). Prefill is not captured — its shapes change every request and the kernels are big enough that launch overhead does not matter. `--enforce-eager` also switches off `torch.compile`, so you lose kernel fusion (several small ops merged into one kernel) at the same time as losing graphs; E15's 63 ms figure is the sum of both losses, which is why it undershot the "launch gaps only" hypothesis by 3×.

**Why speculation softens the blow, and why that matters for E6.** In eager mode DSpark still gave 49.5 tok/s (vs 15.9 without): the CPU-bound step costs the same ~63 ms whether it verifies 1 token or 6, so accepting ~4 tokens per step amortises the overhead 3×. That is the E10 idea in miniature — and the reason the E6 hybrid engine design says the GPU half of the step **must** stay capturable even though the CPU experts run outside the graph. The tools for that are `cudaLaunchHostFunc` (a host callback recorded inside the graph) or KTransformers' submit-and-sync pattern, where the graph waits on an event the CPU thread signals when its expert GEMV is done. An eager hybrid step would put 63 ms of Python on top of the ~20 ms CPU expert time and land at ~12 tok/s; a captured one keeps the GPU side at 11 ms and the total near 30 ms — the difference between "unusable" and "usable" for V4.1 on two cards.

**What to read.** NVIDIA blog "Getting Started with CUDA Graphs" (the one-page mental model); CUDA Programming Guide §3.2.8 (graphs, capture, `cudaLaunchHostFunc`); vLLM docs "CUDA graph / compilation config" and the source `vllm/compilation/cuda_graph.py` and `vllm/v1/worker/gpu_model_runner.py` (search `capture`); PyTorch `torch.cuda.CUDAGraph` docs for the raw API. Evidence on this box: [`evidence/e15-t24-v4-flash/`](../evidence/e15-t24-v4-flash/) and BENCHMARKS.md §E15.

**How to see it yourself.** With the V4-Flash sibling running, watch `nvidia-smi --query-gpu=power.draw,utilization.gpu -lms 500` during `bench-decode.py --concurrency 1`: graphs → ~240 W steady; eager (`EAGER=1` in a `RECIPE_ENV_FILE`) → ~150 W with utilization flickering. The power meter is a launch-overhead detector.
